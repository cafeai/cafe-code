# macOS closed-lid work

General → Desktop exposes **Work with the lid closed** only through the macOS desktop preload. `ClientSettings.keepAwakeWithLidClosed` defaults to `false`, including decoding older preferences. It is a primary-machine preference even when the renderer selects a remote environment. Linux, Windows and browser clients have no native capability. The existing **Keep awake** preference is preserved: its display blocker applies with the lid open, while an exact closed-lid work owner temporarily permits the screen to sleep.

The new toggle prevents idle system sleep while the primary local backend has starting/running root work or current active background work. It keeps no display-sleep assertion alive. With only the built-in display connected, closing the lid requests immediate display sleep and reopening wakes it once while work continues. A long healthy chat may renew its system-sleep request without an arbitrary job deadline. Battery at or below 20%, unknown battery/power state and serious/critical thermal pressure release the native request; current fresh intent may resume after those conditions clear. Normal macOS explicit Sleep, restart and shutdown are not converted into application jobs. This is not a thermal or battery-management substitute.

## Intent and ownership

The exact spawned desktop backend inherits a dedicated output pipe on fd 5, admitted only by its private bootstrap. The server publishes one bounded, content-free record per second: version, safe monotonic sequence, enabled and work-active booleans. Nothing is exposed through a public environment descriptor, HTTP endpoint or provider session. Standalone servers and provider daemons cannot acquire this capability. The disabled path does not query work or spawn a native helper.

The work query reuses the projection's canonical session/turn reconciliation and its exact current background-work binding CTE, including the provider-runtime, explicit-start and child-task owner. It does not hydrate transcripts, ordinary activity history, titles or provider credentials, probe providers, or use the selected renderer workspace. Terminal/stopped or foreign-runtime work cannot grant intent. Root lifecycle rows are bounded at 4096 candidates; overflow conservatively indicates possible work rather than loading unbounded history or claiming it is idle. Current exact background work remains eligible after the root turn completes.

The desktop binds one owner per actual backend incarnation, before spawn. A malformed, oversized, replayed or ended stream retires that owner. A five-second lease uses both monotonic and wall-clock age so stale observations cannot be revived across a clock change or machine sleep. Old owner callbacks, late startup results and previous native status cannot refresh the next incarnation. Native close must complete before replacement admission.

Turning the toggle off also revokes input synchronously through trusted main-frame IPC before attempting preference persistence. A failed disk write or old enabled heartbeat cannot undo that choice during this desktop lifetime. Turning it on only clears this revocation; it still needs fresh authoritative backend preference and work. Individual reset and whole-page reset use the same revocation. Native errors become fixed status categories, never native error objects or output text. Unexpected native failures latch until intent is deliberately rearmed or current work transitions to idle and starts again; ordinary refreshes do not create a restart loop. A refused reset retains the unavailable status and exact native reservation even after Off. It cannot admit a competing helper or silently claim recovery; checking physical sleep behavior remains necessary.

## Native lease and recovery

The bundled Swift helper owns a supervisor and a worker in independent process groups. The worker holds an eight-second `PreventUserIdleSystemSleep` assertion, renews its timeout only after fresh private input, and uses `IOPMrootDomain` selector `kPMSetClamshellSleepState` to disable lid-triggered sleep. Because powerd can rewrite that shared bit around display/power transitions, each admitted renewal reapplies it after checking freshness again around assertion IO; ordinary policy polls never rearm it. Neither process makes a persistent `pmset` change. No administrator password, privileged helper, sudoers rule, login item, provider command or PID catalogue is involved.

The parent and worker exchange bounded private messages. Each has a four-second continuous-clock heartbeat, including machine sleep in elapsed age. Queued input cannot revive an expired owner. The supervisor waits for worker readiness before permitting its first lid change and observes actual worker renewals. On cancellation it closes that exact worker's input, joins its native exit, then resets the raw switch. A frozen worker gets one second of close grace before only that unreaped child is killed. An exited/frozen supervisor loses its worker heartbeat, and the surviving worker resets the switch itself. Loss of the desktop closes the supervisor's pipe. The OS assertion timeout separately bounds a frozen worker's idle-sleep assertion.

Disabling clamshell system sleep alone can leave the built-in panel illuminated when there is no external monitor. The worker reads the actual `AppleClamshellState` at its existing 250 ms native timer and before display actions. With a current lease, a closed lid and an online display inventory containing only built-in panels, it makes the same transient display-idle request as Apple's [`pmset displaysleepnow`](https://github.com/apple-oss-distributions/PowerManagement/blob/main/pmset/pmset.m): `SLSDisplayManagerRequestDisplaysIdle` from the fixed system SkyLight framework, with the legacy `IODisplayWrangler` `IORequestIdle` fallback when the symbol is unavailable **or the modern request is refused**. It then renews the lid override only if work is still fresh. This does not change brightness, saved display configuration or power preferences, and does not launch an independent command that could act after retirement.

Display enumeration, display-idle refusal and failure to declare a wake pulse do not tear down healthy work's independent sleep protection. Unknown inventory excludes display writes; a later qualified inventory may recover. A sleep request is reserved once even if refused, so polls cannot repeatedly send it. These failures emit only fixed, content-free phases to the `com.cafeai.cafecode` / `mac-power` native log. Refusal to **release an already-created user-activity assertion** is different: the owning helper retires so process exit releases any possibly-held assertion. Native pipe/lease, power, thermal and raw-switch reset failures retain their existing retirement policy.

That display-idle API affects all displays, so an observed external, mirrored or virtual monitor excludes this request and leaves macOS clamshell display behavior in charge. The inventory is a snapshot, not an atomic hotplug guarantee. Unknown lid state never authorizes an action. Reopening after Cafe's own sleep request issues one [`IOPMAssertionDeclareUserActivity`](https://developer.apple.com/documentation/iokit/1557127-iopmassertiondeclareuseractivity) pulse and immediately releases its assertion. Polls and work renewals do not repeatedly reset the screen's idle timer, and the pulse does not unlock the session. A quick reopen during the synchronous sleep request is checked before returning.

### Coordinating the ordinary display blocker

The physical lid sensor is independent of display power. The helper reads `AppleClamshellState`; the native host observation of lid-open pulses confirms actual closed/open detection, not successful panel power-off. An ordinary **Keep awake → During chats/Always** request also holds Electron's `prevent-display-sleep` blocker. It must be coordinated with closed-lid work rather than left competing with a display-idle request.

Each exact native attempt binds one temporary display-policy owner. An observed closed lid with built-in-only inventory synchronously revokes prior adoption and coalesces application to one held operation plus the latest policy. When the ordinary preference requires a blocker, Electron starts `prevent-app-suspension` before releasing its exact display blocker, then confirms release through `isStarted`. It acknowledges display sleep only after actual adoption. Opening the lid, observing an external display or retiring that owner restores the ordinary preference without rewriting settings. Unknown lid/inventory withdraws new screen-sleep permission while retaining the current blocker policy, so it cannot relight an already sleeping panel. A failed native stop retains its exact ID; the replacement set cannot exceed two IDs. Retirement joins pending application before another display-policy owner is admitted, and service finalization joins the driver before releasing its native blockers.

With **Keep awake → During chats** and **Work with the lid closed** enabled, an active chat keeps the open-lid screen awake, closing the lid releases display protection while work remains protected, and reopening restores display protection if the chat is still active. Ending the chat releases its ordinary blocker; opening the lid afterward cannot recreate it from a stale chat-start update. The Off and Always preferences keep their existing meanings.

Every admitted lid observation, owner change and ordinary preference/chat update replaces an in-memory revision identity and revokes adoption synchronously. An application captures that exact revision and rechecks it after native observations and operations, before another stop, and before publishing adoption. An already admitted native operation must finish: a late start retains its returned exact ID for the latest policy to reconcile, while a late stop cannot release an additional ID under superseded intent. The same final closed boolean after a rapid close/open/close does not reuse an older revision. Ordinary updates publish desired state before mutex admission, so queued applications read the latest intent rather than replaying old starts and finishes. Once published, that admitted reconciliation joins native completion even if its IPC waiter is cancelled; service retirement still fences writes and joins the mutex. Failure of an older operation cannot clear newer pending intent or revoke a newer completed adoption; it does not cause an automatic same-intent retry loop.

The desktop echoes a safe, increasing lid/inventory sequence with the display-policy acknowledgement on a fresh work renewal. The supervisor maps it to the exact current worker observation; that worker revokes the permission synchronously on any physical or topology transition and rejects an older observation token. Initial, unknown, changed and replacement-worker observations withdraw permission. A cached closed flag, delayed completion, old child, stale acknowledgement or ordinary policy poll cannot authorize screen sleep. The helper still rechecks the physical lid, current lease and display inventory immediately before native IO. Negotiated coordination never downgrades to the legacy protocol during an attempt; older parents retain their existing wire format and behavior until restarted.

Before display sleep, the worker reserves its request through the existing private `alive` envelope. Only successful wake clears that reservation at the supervisor. After joining the exact worker's native exit, the supervisor drains its remaining bounded pipe messages before deciding cleanup, then wakes once only if an owned request remains and the actual lid is open. Normal retirement also avoids lighting a closed panel. This recovery stays under the same flock as the raw-switch reset. An unavailable transient wake is logged; it cannot retain a completed raw-switch lease as `cleanup-failed`, because there is no persistent panel-disable setting to restore. Normal macOS input/wake remains available if both helpers disappear; the shared raw lid-switch limitation below still applies.

Both native processes retain the same open-file-description `flock` through reset and native exit. Its per-UID `/private/tmp` directory is private and opened without following a symlink; its descriptor-relative lock is a private, regular, single-link, no-follow file. A second Cafe instance is refused rather than controlling another instance's PID or racing a late reset. It may retry when its work restarts or the user toggles off/on. Source launches compile the fixed helper before launch; artifact staging builds the selected architecture and includes it as a normal signed resource.

The raw lid switch is shared system state, **not a process-scoped assertion or a public macOS power API**. Amphetamine Enhancer's published implementation uses this selector, and Apple's XNU source defines its clamshell notification behavior. Reset success means the kernel accepted Cafe's reset request. `AppleClamshellCausesSleep` can remain stale when resetting with the lid open, so it is not reset-failure authority. See [Amphetamine Enhancer](https://github.com/x74353/Amphetamine-Enhancer/blob/master/Xcode%20Project/CDMManager/CDMManager/AppDelegate.m) and [IOPMrootDomain](https://github.com/apple-oss-distributions/xnu/blob/main/iokit/Kernel/IOPMrootDomain.cpp).

Recovery covers loss or suspension of one native process while the other can execute. Simultaneously killing both native processes, kernel refusal, or another app manipulating the same shared switch cannot be made crash-proof by this unprivileged helper. Competing sleep utilities are not coordinated. The assertion times out even if both helpers disappear, but the raw lid bit itself has no OS lease. Do not claim universal hardware/macOS compatibility or guaranteed normal sleep from an ACK. This implementation remains an opt-in native path, and a release still needs its normal signing and native artifact qualification.

## Verification

Pure tests cover strict frame parsing and bounds, default-off settings, stale/replayed owners, wall-clock changes, synchronous revocation, native startup/close handoff and failure latching. Projection tests cover reconciled root and exact current background work. Native browser tests exercise the real switch, primary settings updates and capability gating. They do not grant native power authority.

Run the opt-in native qualifier on macOS:

```sh
nice -n 10 corepack yarn workspace @cafecode/desktop test:mac-keep-awake
nice -n 10 corepack yarn workspace @cafecode/desktop test:mac-keep-awake --live
```

The ordinary qualifier compiles a separate test-only helper into a private temporary directory. It uses fake power/display state to exercise repeated lid-close/open transitions while work stays active, no repeated display requests across actual native timer observations, external/unknown display exclusion, closed-panel cleanup, fallback after a refused modern request, continued work and eventual expiry after refused display control, inventory recovery, fresh-input-only restoration of a rewritten lid bit, unavailable wake cleanup, fatal wake-assertion release failure, heartbeat expiry, malformed input, individual supervisor/worker crashes and suspension, exclusive ownership, and unsafe lock refusal. Crash/freeze display recovery holds the exact worker before changing the fake lid so its joined supervisor must perform any recovery wake. Its test-only fault/observation commands are absent from the production build. Completion and timeout retirement are registered before native acquisition; cleanup joins the exact held children before removing their private files.

Display-policy unit tests cover both ordinary keep-awake modes, preserving Off, actual native adoption, held/refused release, bounded replacement ownership, noncurrent/retired callbacks and joined cleanup. Synthetic native-pipe tests cover sequence echo, external/unknown inventory, unknown/pause revocation, owner retirement and replay/malformed refusal. The opt-in native qualifier additionally holds display permission while real native timer observations continue, then proves that only an acknowledgement for the current physical-lid and built-in-only inventory observation admits the one-shot action, including after a topology change.

Deterministic Deferred gates additionally hold real service operations across reopening, rapid close/open/close, an older refused stop, queued chat start/finish updates and cancellation of an admitted chat-stop waiter. They assert actual retained/released blocker IDs, uninterrupted existing CPU/display protection where still required, no screen-sleep adoption while a late display blocker remains, no stale chat-start resurrection and eventual release after cancelled waiters. These checks use neither timing sleeps nor native-input replay and do not qualify physical panel power-off.

`--live` makes a real temporary power request while the lid is open. It checks that the idle assertion renews beyond its eight-second OS timeout, creates no held display assertion, receives reset acknowledgement and leaves no Cafe work assertion after shutdown. It does not deliberately blank an open screen or prove physical lid/display/sleep behavior. The earlier standalone prototype was separately tested by the owner with the lid closed, and the owner confirmed normal sleep afterward. The subsequent integrated screen-off change needs a separate physical close/open check; a read-only API/topology probe and fake-native results cannot establish that hardware behavior. Integrated physical testing across battery/AC changes, suspend/resume, thermal transitions and other macOS versions remains separate native-host qualification. Normal tests do not open providers or use real credentials.

Live qualification requires the shared Cafe power lease to be free. An already active Cafe assertion or a native `lease-busy` admission refusal is reported as an explicit skip; the qualifier never stops another session, changes its preference or bypasses the common lock. The fake-power exclusive-owner and crash/expiry checks remain required assertions. Run the opt-in live check on an idle test machine to obtain fresh physical power-request evidence.
