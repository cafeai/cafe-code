# AGENTS.md

## Task Completion Requirements

- This repository is Yarn-and-Node-only. Use the repository-pinned Yarn 4.17.1 release through Corepack for package operations and Node for JavaScript/TypeScript execution. Do not add or invoke any alternate JavaScript runtime or package manager in source, tests, fixtures, documentation, scripts, or CI.
- When code changes are made, all of `yarn fmt`, `yarn lint`, and `yarn typecheck` must pass before considering tasks completed.
- Run tests with `yarn test` (runs Vitest through the Turbo task graph).
- After tests complete for any software change, run `yarn build:desktop --force` as the final verification step. The forced desktop build is required even when the change does not directly touch Electron packaging, backend bootstrap, provider daemon startup, or generated bundle boundaries.
- Rust takes a while to compile. Do not prematurely kill Rust/cargo builds.
- Integration tests that require live provider binaries, real provider credentials, process reaping, or detached daemon handoff should be explicit `*.e2e.test.ts` or documented opt-in commands. Do not silently put flaky external-provider assumptions on the default test path.

## Search Discipline

- Prefer `rg` and `rg --files` for source discovery. Do not run broad `find` searches from `/`, `/usr`, `/opt`, `/Users`, or other high-level roots unless the task absolutely requires it and the reason is stated first.
- Keep filesystem searches targeted to the repository subtree or a specific known parent directory. Exclude generated and dependency-heavy directories such as `node_modules`, `target`, `__pycache__`, `.git`, `.turbo`, `.astro`, `dist`, and `build`.
- When `find` is necessary, use bounded roots plus pruning/exclusion predicates instead of scanning the whole machine.

## Project Snapshot

Cafe Code is a desktop GUI for coding agents such as Codex, Claude, and OpenCode. Cursor was retired; its historical settings and persisted thread references must decode safely but should be filtered out of runtime registries and provider settings UI rather than surfaced as an unavailable first-party provider. The project is still early and inherited code may be incorrect or overfit to older fork behavior. Prefer evidence-backed fixes, strong diagnostics, and maintainable redesigns over small patches that only hide symptoms.

Core priorities:

1. Performance first.
2. Reliability first.
3. Security first.
4. Treat 16+ hour provider prompts as a normal target workload, not an edge case.
5. Keep behavior predictable under load and during failures such as restarts, provider crashes, partial streams, delayed provider wakeups, and reconnects.

If a tradeoff is required, choose correctness, durability, and debuggability over short-term convenience.

## Security Requirements

- Write all code as if it will run in a security-conscious environment where adversaries will constantly try to attack local transports, provider sessions, provider credentials, persisted command ledgers, and debug surfaces.
- Local provider daemon and supervisor transports must be loopback-only or IPC by default, authenticated with high-entropy capability tokens, and must never be exposed on a non-loopback interface without an explicit authenticated design.
- Secrets such as provider daemon tokens, Codex auth, Claude credentials, OpenCode server passwords, saved-environment bearer sessions, and app bootstrap credentials must be stored as private files with restrictive permissions where the platform supports them. Never persist secrets in logs, debug JSON, process argv, browser local storage, or user-visible error strings.
- Do not symlink auth files into shadow homes. Copy private auth files when needed, chmod them to `0600`, and reject unsafe symlinked auth material.
- Debug endpoints may expose operational diagnostics but must not expose raw prompts, full model outputs, bearer tokens, cookies, auth JSON, API keys, or unrestricted filesystem paths unless the user explicitly asks for a local forensic dump.
- Any change touching provider process ownership, daemon handoff, provider-home materialization, approval handling, command execution, or debug output needs a quick security audit and tests for the failure mode being addressed.
- Inform the user when security-related behavior changes.

## Maintainability

- Long-term maintainability is a core priority. If you add functionality, first check for shared logic that belongs in a separate module. Duplicate lifecycle or provider-connection logic across files is a code smell.
- Do not write stubs or incomplete code. Finish the behavior, tests, diagnostics, and cleanup needed for the requested change.
- Prefer structured schemas, generated protocol types, durable state machines, and explicit event names over stringly-typed local conventions.
- Add verbose comments for non-obvious code. Lifecycle, provider connection, daemon/supervisor, auth, persistence, and protocol-boundary code should be especially well commented.
- Comments should explain why a state transition, timeout, reconciliation step, security check, or provider protocol workaround exists. Do not leave lifecycle code with unexplained magic constants or unexplained "best effort" branches.
- When implementing Codex, Claude, or other provider protocol behavior, reference official docs and, where available, the provider's current SDK types or open-source implementation. Record important source-derived assumptions in comments near the code that depends on them.
- Keep this file's architecture sections current. Any change that modifies how a provider starts, resumes, streams, retries, falls back, asks for approval, persists session identity, hands off to a daemon/supervisor, or reports diagnostics must update the matching provider section below so future agents inherit the current design instead of stale fork assumptions.
- Periodically re-check upstream provider implementations when pinned CLIs/SDKs change, especially under-development feature flags, default-enabled feature flags, request config keys, model/tool metadata, and lifecycle contracts. Cafe should intentionally track upstream behavior where it is stable, and should keep local compatibility pins or quarantines documented until upstream behavior is verified safe for Cafe's long-running workloads.

## Package Roles

- `apps/desktop`: Electron main process, desktop bootstrap, debug server, backend process manager, provider daemon manager, and local process reaper. This is where app startup decides whether to adopt, spawn, stop, or leave detached runtime processes alive.
- `apps/server`: Node.js backend and provider runtime host. It serves the web assets, exposes HTTP/HTTPS and WebSocket/API surfaces, owns orchestration, persistence, provider adapters, the provider daemon HTTP/RPC server, and provider supervisor support.
- `apps/web`: React/Vite Electron renderer and browser Web UI. It owns session UX, message timelines, scroll behavior, settings UI, and client-side state. It receives orchestration domain events from the backend and must not invent provider lifecycle state that the backend did not emit.
- `packages/contracts`: Shared Effect Schema contracts for provider runtime events, orchestration events, daemon RPC/health, supervisor metadata, WebSocket/API protocol, desktop bootstrap, settings, and model/session types. Keep this package schema-only; do not add runtime business logic.
- `packages/shared`: Shared runtime utilities consumed by server, desktop, and web. Use explicit subpath exports such as `@cafecode/shared/git`; avoid barrel indexes.
- `packages/effect-codex-app-server`: Typed Codex app-server JSON-RPC client/protocol surface. Keep this aligned with the Codex version we are targeting.

## Provider Status And Maintenance

- `ProviderRegistry` is the sole production owner of initial provider-status refresh admission. Keep initial CLI probes bounded to two concurrent instances, and do not add independent Codex or Claude startup probe fibers that bypass that aggregate limit. An externally admitted managed provider must not start its periodic clock until that initial refresh settles. Periodic probes then use a deterministic phase derived from the stable provider instance id: the first periodic check runs after one full interval plus that phase, then repeats at the normal interval. Renderer config subscriptions are read-only and must never trigger provider probes during reconnect.
- Codex CLI status probes must be disposable subprocesses with tree-aware cleanup: use an isolated process group on POSIX and the platform child-tree path on Windows. Before releasing the child scope, a timeout sends `SIGTERM`, waits one bounded grace interval for actual process exit, and then sends `SIGKILL` with a second bounded wait; the scope itself keeps `SIGKILL` as the final backstop. This explicit wait is required because Effect's `forceKillAfter` currently bounds signal dispatch rather than the later exit wait. Provider snapshots may report only fixed phase names, bounded outcomes, and durations for runtime-home preparation, version, login status, and account usage; never include command text, stdout/stderr, auth state payloads, or unrestricted paths in these diagnostics.
- A bounded `codex login status` timeout is inconclusive, not proof that authentication or the provider session failed. When a conclusive cached snapshot exists, retain its auth/status presentation for the first two consecutive inconclusive checks while recording the fresh observation in redacted `probeDiagnostics`; surface the third consecutive timeout, and reset the counter on any conclusive result. Carry an active inconclusive streak across backend/provider reconstruction, but do not double-count the same refresh observation delivered through both the direct result and the provider stream. Reject older delayed observations, and preserve correlated scheduler metadata when direct and stream delivery reorder. Cache historical observation fields but always take interval, phase, and next-wakeup fields from the new provider scope. Never apply this retention to a real unauthenticated/error response, and never add raw command output, command lines, paths, account identifiers, or credential material to probe diagnostics.
- Provider package updates mutate process-global package-manager state. Build one `ProviderMaintenanceRunner` at the WebSocket route-layer boundary, share its instance/lock coordinator across all connections, and fork an admitted update into that server-owned scope before waiting. A renderer reconnect may stop waiting but must not cancel the update; abnormal worker termination must publish a sanitized terminal state and release ownership. Update state remains deliberately volatile across a full backend restart.
- Config-stream retries and renderer animation fallbacks reconcile provider-update UI from authoritative snapshots; elapsed-time heuristics must never invent update completion. In desktop debug mode, provider fleet summaries must be stable, bounded, and allowlisted, and expensive renderer snapshots must remain capped at one publication per second so diagnostics do not become a source of UI lag.

## Browser Web UI and Local HTTPS

- The browser Web UI is a first-class remote surface. Any shared renderer feature that opens editors, terminals, paths, folders, or OS dialogs must be gated on explicit local host capability and should use copy-path/copy-command alternatives in pure browser or reverse-proxy sessions.
- Detailed usage statistics are owned by one primary-environment, in-memory resource shared by Atrium and Settings. It retains only the last successful result across component unmounts, single-flights refreshes, polls while consumers exist, and schedules one immediate refresh from the exact primary transport's successful-reopen signal while keeping stale data visible. Do not use the global connection-status atom for this refresh because saved-environment transports also publish there. Atrium must prioritize this small control read before admitting its bounded thread-detail hydration, and must show a stable graph placeholder during a true cold load. Do not persist the shared response, duplicate polling loops in components, or let a delayed pre-reconnect result replace newer data.
- Shared renderer copy controls must route through `apps/web/src/lib/copyToClipboard.ts`. Electron uses the required, write-only `DesktopBridge.copyText` IPC method after the existing trusted top-level sender validation; do not add clipboard-read access or log copied content. Browser clients try the modern Clipboard API and may use the selection-based compatibility fallback, which must restore the user's prior focus and DOM selection before returning. Keep native IPC decoding and real-browser fallback behavior covered by tests whenever this path changes.
- After an authenticated backend connection is available, renderer `ClientSettings` are backend-authoritative and shared across Electron and browser clients. Local desktop/browser client-settings persistence is only a bootstrap/import fallback before backend settings are available.
- The main backend keeps HTTP available for compatibility and may also serve a self-signed HTTPS/WSS sibling listener on a separate port. In desktop builds, local HTTPS is controlled by an explicit desktop settings toggle, separate from the local-only/network-accessible host exposure toggle. Browser-facing pairing/headless output should prefer HTTPS when it is enabled; Electron desktop bootstrap may keep using HTTP loopback to avoid self-signed certificate handling in the desktop window.
- HTTPS public certificate material belongs under the server TLS directory, but HTTPS private keys are secrets and must live under the server secrets directory with restrictive permissions where supported. Do not log private key material, generated key output, or TLS secrets.
- Provider daemons and provider supervisors must not inherit the app HTTPS listener by default. Keep their existing authenticated loopback or IPC transports unless a separate authenticated TLS design is implemented for those runtime layers.

## OpenAI Realtime Dictation

- Dictation is an opt-in, transcription-only OpenAI Realtime integration. After the owner submits a new key through the dedicated password input and authenticated mutation, the canonical permanent OpenAI API key lives only in the server `ServerSecretStore` under the fixed `openai-realtime-api-key` name with the store's restrictive file permissions. Clear the transient input before awaiting the mutation response, never return the stored value, and never place it in `ServerSettings`, `ClientSettings`, renderer persistence/caches, debug output, traces, logs, process arguments, URLs, or public error causes. Clients may read only configured/manageable booleans; only an authenticated owner may set or clear the key.
- The server mints short-lived transcription client secrets through the fixed OpenAI `/v1/realtime/client_secrets` origin with redirects disabled, a bounded response body, a timeout, sanitized status-only errors, tracing disabled, and a per-authenticated-session issuance limit. Token-bound configuration uses the versioned `transcription_pcm24k_minimal_v1` profile: transcription session, PCM 24 kHz input, `gpt-live-transcribe`, and manual turn detection, without optional delay or noise-reduction fields. Keep this profile aligned with OpenAI's documented minimal transcription example; omitting optional controls also removes variables while investigating opaque `/v1/realtime/calls` HTTP 500s, but do not claim those controls caused an upstream failure without provider evidence. A stored key is only configured, not proven usable: OpenAI validates its authentication, billing/quota, and Realtime model access when Cafe mints a secret. Permanent-key mutations and ephemeral-secret responses require an observed loopback peer; Cafe's HTTPS sibling terminates TLS and forwards to the backend over loopback. Never trust client-supplied forwarded-protocol headers for this secret boundary.
- The renderer connects directly to OpenAI's WebRTC `/v1/realtime/calls` endpoint using only the short-lived credential and the official ephemeral-token raw `application/sdp` exchange; multipart SDP belongs to OpenAI's separate unified backend-key flow. Preserve allowlisted client-secret RPC error codes and classify call failures only from HTTP status, rebuilding all renderer errors from fixed messages. Retry only transient connection failures and HTTP 408, 409, 429, or 5xx responses, at most twice under the existing setup deadline; never retry authentication or configuration failures. Each retry must mint a fresh credential and create a fresh peer/data channel/offer because OpenAI does not document call-creation replay as idempotent. Keep the one captured microphone stream across those attempts and retire every failed transport before continuing. Do not add `X-Client-Request-Id` to the direct browser request unless OpenAI's `/realtime/calls` CORS preflight explicitly allows it; as of this profile's qualification, that endpoint allows only `Authorization` and `Content-Type`.
- Dictation compact debug is a generation-fenced, 32-entry content-free timeline. It may retain only bounded timings/counts, fixed lifecycle/WebRTC/media enums and booleans, versioned profile/effective-profile facts, finite semantic provider-error categories, bounded `req_`-prefixed OpenAI request IDs, response media/length metadata, a SHA-256 fingerprint of a bounded error-body prefix, and SDP shape facts such as byte/line/media/candidate counts and Opus presence. The renderer must read at most 64 KiB of an error response, never extract its message, and discard temporary body bytes/JSON before recording. The desktop debug boundary must independently revalidate every top-level and timeline field. Never retain or expose API keys, ephemeral credentials, authorization or arbitrary headers, provider messages/bodies, raw errors, SDP text/hashes, ICE addresses/credentials/fingerprints, audio, transcript text, media labels/device IDs, or local paths. Stream transcription delta events into a composer-owned text range, reconcile that range with each authoritative completed transcript, preserve text that existed before dictation, and never submit automatically. Explicit stop commits pending audio and all stop/error/unmount paths must close the data channel and peer connection, settle finalization, and stop every media track.
- The microphone control is shown only when dictation is configured and the renderer has a secure context plus the required media/WebRTC APIs. In Electron, permission handlers grant only audio media requested by the trusted Cafe top-level `webContents` at its exact origin; camera, child frames, replaced web contents, foreign origins, and unrelated permissions fail closed. macOS packaging must retain `NSMicrophoneUsageDescription`.
- Important files are `packages/contracts/src/dictation.ts`, `apps/server/src/dictation/`, `apps/server/src/ws.ts`, `apps/web/src/dictation/`, `apps/web/src/components/chat/ComposerDictationButton.tsx`, `apps/web/src/components/settings/DictationSettings.tsx`, and `apps/desktop/src/window/DesktopWindow.ts`.

## Saved Remote Environments

- The renderer can connect directly to additional, already-reachable Cafe servers through a pairing URL or host plus pairing code. Cafe does not manage SSH, tunnels, Tailscale, DNS, reverse proxies, certificates, or hosted frontend deployment; browser mixed-content and certificate policy remain authoritative.
- Pairing credentials are one-time bootstrap secrets. Exchange them for a bearer session, clear them from UI state immediately, and never persist or retry them. Mint a fresh short-lived WebSocket token from the bearer session for each connection attempt; never place the bearer session in an HTTP or WebSocket URL.
- Desktop saved-environment bearer sessions are encrypted with Electron `safeStorage` in a private `0600` registry where supported. ## Renderer Markdown Math

- Fenced `tex`/`latex` labels are ambiguous: providers use them for both standalone equations and copyable LaTeX document fragments. Convert a closed fence to KaTeX only when every content line is conservatively equation-shaped. Preserve mixed prose, nested math delimiters, labels, theorem environments, and unterminated streaming fences as source code; never wrap an entire LaTeX document fragment in one synthetic `$$...$$` block.
- Chat messages render Markdown through `apps/web/src/components/ChatMarkdown.tsx`. Provider math output is intentionally normalized before Markdown parsing by `apps/web/src/lib/chatMarkdownMath.ts`: Codex commonly emits fenced `math`/`tex`/`latex` blocks, while Claude commonly emits `$...$`, `$$...$$`, `\(...\)`, `\[...\]`, and TeX macros in prose. Preserve all of those shapes when changing message rendering.
- Math rendering uses `remark-math` plus KaTeX through `rehype-katex`; keep KaTeX configured with `trust: false` and non-throwing error handling so malformed or hostile math cannot crash chat rendering or enable trusted HTML-style extensions. Real code fences must remain code fences and must not be reinterpreted as math.
- Slash display math normalization for standalone `\[`/`\]` blocks must preserve matching indentation inside Markdown list or blockquote continuations. Mixed indentation on generated `$$` delimiters can make `remark-math` split the block and render following prose as accidental math. All slash-delimiter normalization must stay code-fence aware so literal TeX examples in non-math fences are never rewritten.
- Claude and Codex can emit multiline dollar-display math with the opening `$$` on the first equation line and/or the closing `$$` at the end of the final equation line. Normalize those blocks into delimiter-only display math before Markdown parsing, preserving indentation and staying code-fence aware. Without this, `remark-math` can hand KaTeX a malformed continuation line and the UI shows raw red `.katex-error` text despite the provider output being valid TeX.
- Provider math can place underscore-heavy source identifiers inside `\texttt{...}` without TeX-escaping the underscores. KaTeX correctly rejects that text-mode syntax, so `chatMarkdownMath.ts` repairs only unescaped underscores inside balanced `\texttt` commands that occur within recognized math spans/blocks. Keep this pass math-only and code-fence/code-span aware, preserve existing `\_` escapes and real math subscripts, and leave the raw persisted provider output unchanged.
- Native chat selection copy is governed by the local `chatCopyFormat` client setting. The default is Markdown source copy for complete single assistant-message selections, using the same math normalization and provider cleanup as rendering/copy buttons so LaTeX remains pasteable into Markdown renderers. The plain-text setting must leave Ctrl-C and right-click Copy on normal browser visible-text behavior.
- Wide Markdown tables/charts in chat must scroll horizontally inside their own message-local container. Do not let tables, display math, long code identifiers, or long URLs widen the message timeline, crush columns into unreadable letter wrapping, or require page-level horizontal scrolling.
- Table overflow belongs to the table scroll wrapper, not to individual cells. Plain prose cells may stay capped and wrap, but cells containing code spans or KaTeX must be allowed to widen the table so unbroken tokens and rendered formulas do not paint across neighboring columns.
- GFM table cells cannot safely contain true block math. If providers emit same-line display delimiters such as `$$...$$` or `\[...\]` inside a table row, normalize them to inline math before Markdown parsing so the table remains structurally valid after reload.
- Codex ChatGPT search output can include private-use citation delimiters such as `U+E200 cite U+E202 <handle> U+E201` around opaque handles like `turn4search3`. These are valid UTF-8 provider markup, not mojibake or a local decoder failure. Cafe must keep raw provider text persisted for diagnostics, but Codex chat display and assistant-copy text should normalize those markers through `apps/web/src/lib/codexCitations.ts` so private-use glyphs do not appear in the UI. Do not fabricate external links unless app-server supplies trusted URL metadata for the handle.

## Renderer Ambiance Layer

- Ambiance is an optional decorative weather layer drawn on one full-window `pointer-events: none` canvas at z-40 (above app content, below z-50 dialogs/popovers and toasts). It is renderer-only decoration: it consumes already-projected store state and must never synthesize provider lifecycle truth, dispatch commands, or feed anything back into orchestration.
- Effects come in two rendering back ends, catalogued once in `apps/web/src/ambiance/ambianceEffects.ts`: canvas-2D (stars, rain, snow, matrix, fire, glass, lattice, blossom) and raw-WebGL fullscreen-quad fragment shaders (aurora, grid, horizon, resonance, converge, beam, terminal, core). There is no three.js and no scene graph — the shaders are GLSL strings over one oversized triangle. A canvas holds exactly one context type, so `AmbianceLayer` keys its canvas element on the back end and rebuilds the engine when the selected effect crosses that boundary; `AmbianceEngine.dispose()` releases the GL context via `WEBGL_lose_context` rather than leaving it resident. If a GL context or shader cannot be created the engine falls back to a canvas-2D effect — a decoration must never render as a blank screen.
- Both back ends consume the same signals: the 2D effects read `drive`/`wind`/`speedMul()`/`stateColor()` directly, and the GL effects receive them as `u_drive`/`u_wind`/`u_burst`/`u_fog`/`u_fault`/`u_clearing`/`u_hold`/`u_tint` uniforms, so a shader reacts to a thread exactly as rain does. Shaders output alpha (never an opaque background) because the layer sits over live app content, and per-surface clipping becomes a `u_side` discard instead of `ctx.clip()`.
- Every effect renders in both themes. `AmbianceEngineConfig.dark` carries the resolved app theme; the 2D engine routes all colour through `ink()`/`lift()`/`alphaK()` and the shaders through `themeOut()`, which darkens the glow into a stain and lifts alpha on a light ground. Additive blending (fire) is only used on dark. The settings tiles label each effect's GPU cost (light/medium/heavy, plus a `GPU` marker for WebGL) because the catalog now spans a 50-node 2D graph up to a per-pixel volumetric orb.
- Switching effects must rebuild whatever the new effect needs. A shader compiles its program once at construction, so `AmbianceLayer` keys its canvas and engine on `webgl:<effect>` for GL effects and a shared `2d` for canvas effects: keying on the back end alone left the layer running the previously compiled program, so picking a different GPU effect changed nothing on screen. The 2D effects deliberately share one engine and swap through `setConfig`, keeping their pools so the new effect fades in from a mid-state.
- `ambianceOpacity` is a CSS opacity on the canvas rather than an engine value, so it applies identically to both back ends at no per-frame cost. It is a separate axis from intensity: intensity sets how busy the sky is, opacity how strongly it reads.
- All ambiance preferences are flat `ambiance*` keys in `ClientSettingsSchema`/`ClientSettingsPatch` (enabled, effect, intensity, opacity, react mode, per-surface toggles, color, plus the Task Atrium keys). Ambiance ships disabled by default so fresh installs keep the plain sidebar stars; the Settings → Ambiance tab (`/settings/ambiance`) edits it with the standard `SettingsRow` grammar, and the restore-defaults flow covers the whole group.
- Weather color resolution order is: explicit ambiance color, then the Appearance accent color, then the sidebar color, then the theme's computed `--cafe-sidebar-accent`. ## Current Runtime Architecture

Cafe Code has three important runtime layers:

- Electron desktop process: starts the UI, starts/adopts the main backend, starts/adopts the provider daemon, exposes a local debug endpoint, and performs process cleanup when the user exits.
- Main backend/server: owns app-level orchestration, event sourcing, projections, settings, WebSocket pushes, HTTP routes, and durable persistence.
- Provider runtime process: the provider daemon owns long-running provider adapters and live sessions by default so provider work can survive UI/backend restarts when possible. A persistent provider supervisor still exists as an explicit runtime role, but automatic provider-daemon handoff to that extra supervisor hop is disabled until supervisor restart/fallback preserves the provider registry and active-session truth under dead IPC sockets.
- Renderer environment runtime: the renderer always has one primary backend connection and may hydrate additional saved Cafe server connections. Every connection owns its authenticated RPC client and projection subscriptions; environment routing must remain explicit and must not change the primary backend's identity.
- Packaged desktop updates use stable `latest` or prerelease `nightly` GitHub Release feeds. Eligible builds check after startup and on a bounded poll without automatic download. Unsigned Windows x64 NSIS and Linux x64 AppImage builds expose explicit user-driven download/install, while unsigned macOS arm64/x64 builds expose detection plus an exact GitHub release link for manual DMG replacement because Squirrel.Mac requires code signing. Tagged releases validate manifest asset sizes and SHA-512 hashes before publication, then run a lower-version packaged AppImage detection-only probe against the public feed. Source-checkout Git branch diagnostics remain separate from packaged releases.
- The desktop backend manager treats both sustained repeated backend HTTP health failures and bootstrap readiness timeouts as terminal backend run conditions even if the child process remains alive after termination is requested. This prevents a split-brain state where the backend PID is still present but the HTTP listener is gone, leaving the renderer unable to reconnect and blocking the manager forever on process `exitCode`. The post-readiness watchdog is intentionally more patient than bootstrap readiness because large long-running workspaces can briefly push SQLite/projection work over a one-second health probe. Do not lower the watchdog to short one-second failure windows; brief missed probes should log and recover, while a sustained outage should still restart the backend. On replacement startup, stale desktop backend children are reaped before binding the new backend; provider daemon/supervisor processes are intentionally excluded so provider sessions can survive the recovery.
- The desktop checks the detached provider daemon every five seconds through the capability-authenticated `/api/provider-daemon/liveness` route. That route is a database-free process-identity boundary and must never read provider adapters, SQLite, journals, command ledgers, projections, or supervisor state. The richer `/api/provider-daemon/health` route remains available for cached debug/settings diagnostics, but it must never drive destructive watchdog recovery: on very large long-running databases, its diagnostic reads can legitimately exceed the request timeout while the daemon and provider sessions remain alive. Database-free does not mean event-loop-independent: the daemon uses synchronous SQLite, so lock waits, commits, checkpoints, and filesystem stalls can delay every HTTP handler. Liveness failures are therefore advisory while the recorded daemon PID is alive or process exit cannot be confirmed. Three consecutive failures log sustained unavailability but must not replace that process; a confirmed dead PID triggers recovery after the first failed probe. Recovery stops the backend first, replaces the authenticated daemon, and then starts a backend with the replacement daemon's newly issued lease. The daemon lease is inherited bootstrap capability data and must never be mutated in a running backend or copied through process argv/environment. Preserve and test both the live-but-unresponsive no-recovery boundary and the confirmed-exit stop-backend -> recover-daemon -> start-backend order.
- A detached provider daemon must not keep stdout/stderr pipes owned by Electron. Those pipes close when the desktop process restarts and can kill the surviving daemon with `EPIPE` on a later log write. Provider daemon and supervisor stdio therefore stays ignored, while each child owns a role-specific durable trace (`provider-daemon.trace.ndjson` or `provider-supervisor.trace.ndjson`) plus the existing bounded provider event logs. Do not redirect both detached runtimes into the backend's rotating `server.trace.ndjson`, because independent processes cannot safely coordinate that file's rotation.
- Yarn source and staged artifact installs use the `@cafecode/desktop-runtime` workspace postinstall as the trusted `scripts/ensure-desktop-runtime.ts` boundary. Keep the verifier on this workspace instead of the root package: Yarn must finish the workspace's Electron and `node-pty` dependency builds before verification, especially when Linux compiles `node-pty` from source. The verifier checks the pinned Electron binary and, on macOS, restores executable bits on the exact `node-pty` `spawn-helper` selected alongside `pty.node`; node-pty compiles and consumes that helper only on macOS, while Linux validly builds only `pty.node` and uses `forkpty` directly. Open the macOS helper with `O_NOFOLLOW` and mutate permissions through the verified file descriptor so a symlink cannot redirect the chmod operation. Keep third-party lifecycle scripts denied by default except for the explicitly trusted native dependencies in root `dependenciesMeta`.
- `cafe-code killall` and `cafe-code-server killall` are explicit user-requested process termination paths. They scan for Cafe Code launcher, desktop client, main server/backend, and provider daemon/supervisor processes, protect the current command process and its ancestors, terminate children before parents, and avoid printing raw process argv by default because argv can contain sensitive flags or paths.

- Projection, provider-daemon replay, and renderer backpressure are first-class reliability concerns. Long-lived threads can accumulate hundreds of megabytes of activity payload JSON, so hot-path projections and provider replay must avoid global message scans, avoid loading full activity payloads for shell summaries, avoid collapsed-row count/page fetches from the renderer, and keep cleanup/status work such as remote VCS refresh and checkpoint ref pruning off provider turn completion paths. Codex `turn/diff/updated` events can contain tens of megabytes of repeated full-worktree diff text; keep canonical runtime events and native provider logs bounded to a preview plus length/hash metadata, and compact inherited oversized persistent diff rows before provider-daemon replay decodes them so later steer/user-message/progress events are not trapped behind large diff payload replay. Message submit, steer, and queue paths must pin the timeline to the conversation tail without trusting stale virtualizer scroll measurements, because a false "not at end" report can trigger expensive historical rendering and DB work when the user scrolls back down. Current mitigations include thread-scoped message lookup for streaming deltas, SQL-side pending user-input accounting, hot-path projection indexes, turn-scoped work-log page indexes, VCS remote refresh single-flight/cooldown, bounded batched `EXISTS` probes that discover nonempty historical work logs without loading or counting their activities, submit-time bottom pinning, bounded Codex diff runtime events, provider-daemon replay compaction, and asynchronous checkpoint ref pruning.
- Every provider runtime event now crosses one canonical pre-journal compaction boundary with a finite encoded-byte cap. Preserve event/session/thread/turn/item/request identities and lifecycle state, but replace oversized text, command output, raw provider structures, arrays, and deep objects with bounded previews plus length/hash/omission metadata. The same rule applies to in-memory journals, new SQLite rows, and lazy one-row historical repair. An incompatible historical row is replaced in place by a schema-valid cursor tombstone and recorded in a metadata-only quarantine table; the backend reconciles live provider session inventory before advancing past that gap. Never duplicate the malformed body into quarantine or diagnostics.
- Provider-daemon replay is cursor-paged and uses one serialized response writer per client. Respect `response.write()` backpressure and wait for `drain`; subscribe before replay and cursor-dedupe overlap; bound the live queue by both records and UTF-8 bytes; and disconnect only the lagging bridge client when its lane is full. The backend NDJSON reader must keep split UTF-8 sequences as bytes until a complete line exists, pause while an async record is decoded/admitted, enforce line/pending caps, yield under record/byte/time budgets, and advance the bridge cursor only after bounded downstream admission.
- WebSocket orchestration subscriptions share one backend-owned durable event tail and bounded replay ring. Do not restore one SQLite poller per shell/thread subscription. Route shell/thread events before enrichment, use one bounded queue per subscriber, concatenate explicitly classified append-only assistant deltas in order, replace only explicitly classified snapshot-like updates, keep both forms within protected-event barriers, and fail only a slow subscriber with a sanitized resnapshot-required error. Unknown, lifecycle, approval, user-input, user-message, command-result, cursor, and error events are protected by default. Never apply last-write-wins replacement to an append-only provider or orchestration delta.
- Each authenticated WebSocket connection applies a Cafe-owned bulk-output budget at Effect RPC's public stream Ack/pull boundary. Effect RPC writes one stream chunk, waits for the client Ack, and then invokes the next pull; rechunk bulk streams to one logical item per RPC frame and release the prior frame's permit at the start of that next pull, before waiting for an idle live subscription to emit. Releasing only when the next item arrives leaks one retained frame per subscribed thread and eventually blanks histories by exhausting the connection budget. Account actual encoded JSON bytes, reserve connection capacity for unary/control/Ack/interrupt/approval/user-input/heartbeat traffic, cap individual bulk frames and total admitted bulk bytes/events, and release permits on finalization as well. Do not patch Effect, import private RPC internals, or move provider/session ownership into the WebSocket layer. A saturated subscription fails independently with a short resnapshot-required error; it must not disclose event content or block unrelated control RPCs.
- Thread-detail snapshots must not bypass or increase the per-frame WebSocket ceiling. `apps/server/src/websocket/ThreadDetailSnapshotStream.ts` keeps the legacy one-frame item only when the encoded snapshot fits below one 256 KiB raw chunk (with wrapper headroom); every larger UTF-8 JSON snapshot is emitted as fixed 256 KiB base64 `snapshot-chunk` items identified by a SHA-256 digest. This early chunk boundary prevents one legitimate long-history snapshot from monopolizing the connection-wide bulk budget while another detail view hydrates. `apps/web/src/environments/runtime/threadDetailSnapshotAssembly.ts` enforces finite declared bytes/chunks, exact canonical base64 lengths, ordered metadata, optional Web Crypto digest verification where the browser exposes it, and full contract decoding before one atomic store update. Buffer bounded live events while verification is in flight, then apply them after the snapshot cursor; never expose partial snapshot state or log chunk contents. A malformed assembly is an automatic sanitized resubscribe, not a toast or provider/session failure.
- Provider-pipeline diagnostics are bounded numeric process-lifetime counters plus a fixed event-loop lag window. They may expose counts, byte sizes, cursor positions, durations, percentiles, and overload totals only. Do not add prompts, model output, command text, raw errors, thread/session identifiers, paths, tokens, bearer material, or unbounded labels. Provider-daemon health supplies daemon compaction/writer metrics; backend runtime diagnostics merge those with local bridge, subscription, WebSocket, and event-loop metrics. The daemon/supervisor `activeStreamCount` is the number of connected event-journal consumers, not active model turns, and must never be compared with projected active-turn counts. A supervisor that is intentionally not configured is a neutral `not-configured` layer, not an offline failure.
- Timeline tail following is conditional on user intent. When the viewport is physically at the tail and the user has not tried to review earlier output, streaming row growth should remain pinned. An upward wheel, upward-review touch gesture, Page Up/Home/Arrow Up, Shift+Space, or scrollbar interaction must synchronously cancel every delayed submit/initial hard-scroll and disable LegendList tail maintenance before the next provider row arrives. A stale at-bottom measurement emitted in the same gesture must not re-enable following; re-enable only after a verified return to the physical tail, an explicit scroll-to-bottom action, a thread reset, or a newly submitted local prompt. Keep tail tolerances to a few layout-jitter pixels rather than a viewport-sized distance, and preserve scroll diagnostics for the intent/settle transition.
- Runtime diagnostics must keep provider-daemon event production, backend provider-runtime ingestion, orchestration projection, and renderer-visible freshness as separate signals. A provider can be healthy and still look stuck if daemon events are ahead of the backend ingestion cursor or if projected renderer content timestamps lag behind the daemon's latest event; debug output should show that lag explicitly instead of reporting a generic provider failure or hiding the state. Provider runtime ingestion persists its crash-recovery cursor in batches to protect the SQLite hot path, so live diagnostics must take the maximum of that durable checkpoint and the process-local cursor recorded only after canonical event processing; an idle partial persistence batch is not ingestion lag. Runtime-layer `Last Event` for the daemon comes from the newest bounded runtime-event summary, never daemon process startup time.
- Startup and restart recovery must use shell/detail-scoped projection queries. Do not call the full orchestration snapshot from provider reactors, boot recovery, session reconciliation, health checks, or renderer bootstrap paths; on large long-running databases it can hydrate every persisted message and work-log row into the Electron Node heap and crash startup. Use shell snapshots to identify candidate threads, then bounded thread-detail or turn-page queries for the few threads that truly need body/activity data.
- Provider orphan recovery must merge process-local `ProviderService.listSessions()` state with `ProviderSessionDirectory` durable bindings. A second web/dev backend can have an empty local adapter map while the desktop provider daemon still owns the live turn. Durable positive liveness requires exact `status = running`, a matching `runtimePayload.activeTurnId`, a fresh provider-owner heartbeat, and a still-live owner PID; a bare persisted running row is staleable state, not ownership proof. ProviderService stamps each live binding with a unique process incarnation and refreshes only active-turn rows once per minute, without appending event history or provider text. Dev/browser automation should still use an isolated base/state directory rather than the user's live desktop database. If an older backend already wrote Cafe's `orphaned-active-turn` marker, restore the terminal projection only when the newest durable barrier for that exact turn is that server-authored marker and the current provider runtime still owns the same active turn. A later `thread.turn-interrupt-requested` is an explicit cancellation barrier and always wins. Keep the evidence query thread-scoped and `LIMIT 1`; never scan a multi-hour event stream during startup or runtime ingestion.

## Lifecycle Model

- The renderer requests intent; it does not own provider truth. User actions become orchestration commands/events, then `ProviderCommandReactor` calls `ProviderService`, which routes to the provider daemon or local adapter.
- Provider-daemon RPC failures preserve the daemon's structured error tag on `ProviderAdapterRequestError`. Only an explicit `ProviderUnsupportedError` or `ProviderInstanceNotFoundError` may become “provider instance is not configured”; socket refusal, timeout, authorization, and decode failures are operational runtime errors and must remain distinguishable for recovery. Never infer provider configuration state by parsing or blanket-replacing a human-readable remote error string.
- Provider adapters emit canonical provider runtime events. `ProviderRuntimeIngestion` records them, and projections turn them into renderer-visible state.
- `ProviderRuntimeIngestion` is the owner of ordered provider event flush-through for renderer-visible text. Other provider-event consumers such as `CheckpointReactor` may observe the same `turn.completed` event first, but they must not terminalize a turn from that independent observation until ingestion has published the matching process-local `provider.turn.ingestion-quiesced` receipt. Before ingestion dispatches terminal session state, it must flush every short assistant tail that its projection coalescer still owns; otherwise the terminal projection closes the message and correctly rejects that suffix as stale replay. The receipt means Cafe has processed provider events through the terminal event, flushed assistant/proposed-plan buffers, used any authoritative `item.completed` text, and persisted the provider-daemon cursor for that event. If the receipt never arrives, log the lifecycle problem and avoid dispatching terminal checkpoint/diff state from the checkpoint path rather than closing the turn early and truncating text.
- Provider daemon runtime event replay is a bounded live window, not permanent chat history. Durable provider daemon journals must prune to the configured capacity per runtime owner, but that cleanup must run after daemon socket readiness and in bounded batches rather than inside migrations or pre-listen startup. Replay/backfill code must not make later Codex turns pay for every historical token/runtime event Cafe has ever observed. The main backend persists a provider-daemon runtime ingestion cursor after canonical provider events are processed, then reconnects with only a small replay overlap; do not reset remote provider event streaming to cursor `0` on every backend restart. The daemon-to-supervisor bridge uses its own `provider-supervisor-runtime-ingestion` cursor and must advance it only after the daemon successfully journals a supervisor event, so a daemon restart does not re-read the supervisor's full retained window while still preserving missed supervisor events after crashes. Provider daemon event persistence is idempotent by canonical runtime `eventId`, so supervisor replay after daemon restart fills gaps without appending the same retained supervisor window again.
- Provider-daemon event streams must install the live listener before capturing a durable replay high-water cursor, replay only `(afterCursor, highWater]`, and admit only records newer than that boundary into the finite live queue. Records observed by the listener at or below the boundary are replay overlap and must be discarded, including callbacks that race boundary assignment. Never subscribe before an unbounded replay or enqueue the same historical rows into both replay and live paths; that duplicate pattern can overflow an otherwise healthy finite queue and cause permanent reconnect churn.
- Automatic provider-daemon to provider-supervisor handoff is quarantined. A dead supervisor IPC socket can leave the daemon reachable while remote inventory reports `configuredInstanceCount = 0`, which then misclassifies valid configured providers such as `claude_astrea` as "not configured in this build." Keep the provider daemon on its local provider runtime unless the supervisor path has health-monitored respawn, fallback to local runtime, registry preservation, active-session reconciliation, and tests for dead/refused supervisor sockets.
- Database migrations run before backend and provider-daemon sockets are ready. Keep them to schema changes, indexes, and small bounded data repairs. Do not run large projection rebuilds, JSON event-store scans, DB-wide backfills, or provider-history reconstruction in startup migrations; those repairs must run after readiness as bounded background/manual jobs so desktop health checks and long-lived provider sessions are not blocked.
- Desktop/provider-daemon/provider-supervisor bootstrap data moves over inherited file descriptors, not argv or environment, so capability tokens are not exposed through process listings. On macOS, inherited child-process pipe descriptors can report as sockets; bootstrap readers must consume socket descriptors directly instead of opening `/dev/fd/<n>`, because duplicating those descriptors can block before timeout handling and leave startup waiting forever for an IPC socket.
- Provider daemon startup must treat a refused or dead IPC socket as recoverable startup debris, not a fatal permanent state. Failed daemon spawn/readiness attempts must kill the attempted child, remove only Cafe-owned daemon marker/credential/socket artifacts, retry once from a clean socket path, and pipe child stdout/stderr into the private rotating child log so bootstrap crashes have evidence without exposing secrets in argv or debug JSON.
- Desktop startup hydrates the login-shell environment once before spawning runtime children. Desktop-spawned backend and provider-daemon children receive `CAFE_CODE_SHELL_ENV_HYDRATED=1`, and the backend must skip its own blocking login-shell PATH probe when that marker is present. Direct server CLI launches without the marker still repair PATH themselves.
- Desktop starts the provider daemon eagerly and overlaps provider daemon health readiness with backend startup. The provider daemon manager publishes an authenticated IPC endpoint as soon as the child is spawned and the private credential/marker are written; backend bootstrap must wait for that endpoint before resolving `DesktopBackendConfiguration`, but it does not need to wait for full daemon health. The backend remote provider client is expected to tolerate the daemon listener still coming up and to retry event streaming.
- Desktop source-install update checks run only for local git checkouts on `main` or `dev`. `DesktopSourceUpdates` fetches the matching `origin/<branch>` ref at startup, every 30 minutes, or when the Settings button asks for a manual refresh, then compares `HEAD` with the fetched remote commit while reporting dirty working-tree state separately. Do not auto-pull, merge, stash, or toast from this checker; it is informational UI only. Settings may show the full hash/dirty details, and the chat header may show a passive low-emphasis badge only when the tracked `main`/`dev` branch is behind. Non-`main`/`dev` branches must be reported as ignored without fetching and must never show the chat-header badge.
- Distinguish every lifecycle phase explicitly: user requested, command accepted, provider session connecting, provider session ready, provider turn accepted, provider runtime started, first provider message/token/tool event, completion/interruption/failure, post-completion late event, and reconciliation.
- Do not mark a turn as truly running merely because a send call returned. Some providers ACK a request before their runtime starts streaming. Track ACK and runtime-start as separate facts.
- Terminal UI state must come from provider completion, interruption, failure, or a documented reconciliation path. If a provider sends content after a terminal event, preserve the content and emit diagnostics rather than silently corrupting the turn.
- Nested-agent presentation uses the provider-neutral canonical `task.started` / `task.progress` / `task.completed` lifecycle. Those payloads may carry `RuntimeSubagentPresentation` with the opaque provider child/task `threadId`, a distinct optional provider `historyId`, bounded optional `label`, `path`, `role`, and `objective`, explicit `waiting|active|completed|failed|stopped` status, and the provider-derived start time. Provider adapters own normalization and status mapping; ingestion must preserve that structured object in durable task activity so renderers never need to parse live provider prose such as `Started /root/audit_ui`. The opaque identities are authorization/coalescing keys, not display text: do not normalize one provider id into another, infer `historyId` from `threadId`, or log either id. User-controlled labels/objectives must stay bounded, single-line, control-character-safe, and absent from debug/log metadata outside the authenticated canonical activity that needs them.
- The bounded thread-detail activity window must not evict the only lifecycle truth for a current-turn subagent. In addition to the ordinary most-recent activity cap and latest plan edge, snapshot queries and the live renderer retain the latest `task.started`, `task.progress`, and `task.completed` activity for each `(turnId, subagent.threadId)` in the latest turn. This is a fixed three-edge maximum per retained child and a hard `MAX_RUNTIME_SUBAGENT_IDENTITIES_PER_TURN` ceiling of 4,096 most-recent identities, not unbounded transcript retention; a server detail read that hits the ceiling emits one bounded metadata-only diagnostic per scoped turn and never logs provider child ids or descriptions. The lifecycle-retention SQL must explicitly constrain both `thread_id` and the thread's `latest_turn_id` before evaluating provider-controlled JSON: SQLite cannot reliably infer that turn predicate through the retained-identity CTE join, and a thread-only scan can synchronously parse an entire multi-hour activity history, starve WebSocket heartbeats, and cause reconnect/resnapshot loops. Coalescing is terminal-monotonic: canonical `task.completed` plus its payload status overrides stale repeated presentation state, delayed/replayed progress cannot resurrect a completed/failed/stopped row, and only a later explicit `task.started` edge may reopen the same provider identity. Legacy `Started`/`Interacted` rows are treated as terminal once their owning turn is historical or terminal so old clients never show them as working forever.
- A subagent control call finishing is not necessarily the nested task finishing. Keep the canonical subagent task active across immediate spawn/send/control-item completion and across partial child output; emit `task.completed` only from an explicit provider child/task terminal status, interruption/stop, non-retrying terminal error, or documented liveness reconciliation. This boundary is independent from aggregate parent-turn completion, which must still wait for the provider-owned root and every registered descendant as described by each adapter.
- Provider subagent detail is a bounded, authenticated history view rather than a transcript copied into task activity. Before the provider is called, prove the exact `(Cafe thread, Cafe turn, child id, optional history id)` tuple against durable structured lifecycle activity and an exact child-history row. Each child row joins an immutable per-turn provider root captured when the turn/event was ingested; that normalized root owns the original provider kind, configured instance, resume cursor, and cwd once for every verified child in the turn, independently of the thread's mutable current session. A later Codex/Claude or account switch can therefore neither misroute an ended child nor borrow the new provider's credentials. Resume cursors and cwd remain server-private and must never enter renderer-visible activity, RPC input, logs, traces, or errors. Fail closed when the exact child row, root, or configured instance is unavailable. Retain at most 4,096 exact child rows, 512 roots, and 8 MiB aggregate private root data per thread; prune children and roots transactionally, preserve immutable-provenance conflict errors as typed/redacted signals, and keep root/child rows under projection-thread cascade ownership.
- The shared provider-neutral detail contract admits only public `user` and `assistant` text after control/bidi sanitization. It retains at most 64 messages, 32 KiB per message, and 128 KiB total public UTF-8 text; oversized messages preserve a typed head/tail omission, and long histories preserve useful beginning context plus the newest tail with typed middle gap markers (at most two) rather than discarding the latest work. Stable Cafe-generated message keys and explicit omitted-message/byte counts keep provider ids and payloads out of the client. Reasoning, hidden/private messages, commands and output, tool arguments/results, native paths/URLs, provider errors, and raw payloads must never cross this DTO or enter its diagnostics.
- Permanent thread deletion is a coordinated provider, ingestion, orchestration, and persistence boundary. Fence the local/remote provider identity first; permanently retire that thread in provider-runtime ingestion and drain work that entered before the fence; then use the orchestration engine's own FIFO control envelopes to install the durable append-only hard-delete tombstone, remove the thread from the engine command read model, and purge its rows. Never replace this sequence with a raw SQL delete or an ingestion drain without an ingress fence. Database guards must reject stale cross-process event, receipt, provider-runtime, subagent-history, checkpoint, and projection inserts/updates for a tombstoned immutable thread id, while unrelated threads remain writable. Per-thread provider mutations—including both sides of a native fork plus restart, heartbeat, and shutdown persistence—must take deterministic bounded lifecycle locks and recheck retirement before writing. Do not await ingestion while holding a provider lifecycle permit.
- When a turn becomes terminal, projections must close any still-streaming assistant messages for that turn. Providers can stop through completion, checkpoint finalization, interruption, or failure without sending a separate non-streaming replacement for every partial message; stale `streaming=true` rows must not keep the renderer's working marker alive after provider truth is idle.
- Provider assistant deltas remain append-only while live, but terminal assistant completion is a canonical replacement boundary. Upstream Codex TUI `rust-v0.144.3` ignores the completed item payload once its stream controller exists and consolidates the controller's accumulated source into one final transcript cell; Cafe mirrors that shape by flushing only its coalesced tail, never calculating a "missing suffix" from a lagging SQL projection, and then emitting one non-streaming replacement event. Because Cafe's provider runtime and SQL projectors are asynchronous, ingestion keeps a fixed-memory SHA-256 commitment to every observed UTF-16 stream code unit. A provider `item.completed` full-text payload may become the replacement text only when all observed deltas cryptographically match its prefix (or when no deltas were observed); divergent completion text must not overwrite live output. This prevents the proven `first chunk + full remainder repeated` renderer corruption and ensures the final full message repairs a projection that had persisted only the first chunk.
- Historical assistant-message repair is explicit and user-triggered from the thread context menu. The renderer may ask the backend to repair every eligible completed assistant message in one selected thread, using retained local `provider_daemon_events` first and then provider-routed upstream history such as Codex app-server `thread/read` when local journal data is missing. It must run after readiness, stay bounded to the selected `threadId`, require terminal non-streaming assistant messages, and apply only prefix-safe suffixes from retained `item.completed` `assistant_message` events or upstream `agentMessage` snapshots. It must not scan all provider history at startup, call raw provider/OpenAI APIs outside the configured provider adapter, repair all threads, reopen terminal turns, restore `activeTurnId`, or mark repaired messages streaming. RPC results, logs, toasts, progress UI, audit activity, and diagnostics may include safe metadata such as counts, lengths, provider, item id, source type, source event id, and result code, but must not expose raw provider text or repair suffixes outside the normal authenticated message update event that applies the repaired content.
- A terminal turn is immutable provider truth for lifecycle purposes. Late or replayed `running` session snapshots for the same provider turn id must not reopen the turn, restore `activeTurnId`, or regress the thread session; a provider-owned new run must arrive under a fresh turn id. The only Cafe-reconciliation exception is the narrow, durably sequence-bound false-orphan repair above: matching live provider ownership plus Cafe's exact latest `orphaned-active-turn` marker may reopen that same interrupted turn with `terminalTurnRecovery = live-provider-continuation`, while any later explicit Stop forbids recovery. If a turn has terminal checkpoint metadata such as `checkpoint_status = ready`, reconcile any other reopened `running` row back to terminal before renderer or command-gate state reads it.
- Stale projected session rows must not block an explicit or persisted provider/model switch. If a thread's current session metadata references a provider instance that is no longer configured, but there is no live provider session that needs resume identity comparison, start the thread's selected configured instance and overwrite the stale session state. The requested/desired provider instance must still validate strictly; only the abandoned prior instance row is treated as stale.
- Provider runtime replay/backfill content for a completed turn is reconciliation data. Preserve any snapshot-only messages or activity, but do not reopen the thread session, mark the turn running, or restore `activeTurnId` from post-completion content/tool events.
- Provider switches and fresh turns must treat stale provider resume state as recoverable. Codex can reject persisted rollout ids with either the historical "no rollout found" response or the `rust-v0.149.1` thread-store response "failed to resolve rollout path ...: file does not exist"; Claude Code can reject persisted resume sessions with "No conversation found", "No message found", or an early process exit before the user prompt is queued. In those cases Cafe should retry exactly once without the persisted resume cursor, clear the stale cursor on a successful fresh start, and emit a work-log runtime warning. Raw `ProviderAdapterProcessError`/process-exit text should stay in logs/diagnostics and must not be presented as the primary user-facing chat error.
- Provider runtime event fanout is a critical reliability boundary. The provider adapter to `ProviderService` fanout and the provider daemon/supervisor to persistent journal bridge must treat malformed individual events, logging failures, SQLite hiccups, and stream termination as recoverable. Log and drop only the bad event, restart terminated adapter/journal subscriptions while the same provider instance is still current, and keep later valid provider events flowing. A live Codex/Claude process may keep writing provider logs after this bridge dies; if the journal stalls while provider logs advance, the UI can show phantom running turns even though upstream completed. Bridge diagnostics must stay metadata-only unless the user explicitly asks for a local forensic dump.
- Late streaming deltas or provider replay for a terminal turn must not reopen assistant `streaming` flags. The projection may preserve snapshot-only text when no completed message exists, but completed message rows stay non-streaming and terminal lifecycle remains authoritative, matching the Codex CLI's ordered terminal view.
- Provider runtime replay/backfill can append older logical events after a newer turn has completed. Projection shell fields such as `latest_turn_id`, session status, active turn, and lifecycle `updated_at` must be monotonic by provider turn request time/observed time, not blindly by append order. Both the SQLite projector and renderer event projector must ignore an older provisional `starting` session with no active provider turn; do not apply that clock rule broadly because legitimate provider terminal events can carry timestamps older than Cafe's local turn request. Provider event fanout is at-least-once and may resume midway after restart: goal lifecycle decisions must use the monotonic canonical goal index hydrated from projections and advanced by ordered goal domain/runtime events, rather than a replayed goal payload that a newer blocked/completed goal already superseded. Stale checkpoint/session/goal backfill is diagnostic/reconciliation data and must not move the renderer back to older provider-owned work.
- A newer concrete turn is durable evidence that an older same-thread running turn is stale. Reconcile those non-latest running rows to `interrupted` at the first newer turn request and clear their assistant streaming markers so renderer lifecycle state cannot show phantom provider work.
- Steer/follow-up behavior must respect active-turn invariants. Starting a new turn while one is starting or running is a bug unless it is explicitly queued or converted into a provider-supported steer operation.
- The orchestration decider is the authoritative final guard for stale renderer submit races. If `thread.turn.start` arrives while the projected session is `starting` or `running`, accept the user message exactly once and emit `thread.turn-steer-requested` even when the projected `activeTurnId` is temporarily null; never reject the user's submission with the one-active-turn invariant. The exception is an explicit provider-instance change, which must remain a turn-start intent because a steer cannot change provider ownership. `ProviderCommandReactor` must resolve durable same-provider steer intent in order against live provider state, steering a materialized turn or submitting the same message as the next turn when none remains. Preserve the original command/message ids and attachments so receipt retries are idempotent and no user input is lost.
- Cafe thread history is provider-agnostic, but live provider sessions and resume cursors are provider-specific. Users must be allowed to switch an idle thread to any configured provider instance; when the target provider driver or continuation identity differs from the existing session, keep the durable thread/messages/work log, start a fresh provider session for the next turn, and never carry a Claude/Codex/custom-instance resume cursor across that boundary. An explicit provider-instance change on `thread.turn.start` must remain a turn start even when stale projected or runtime state still claims the previous provider owns an active turn; never downgrade it to a steer against the old provider. After the replacement provider accepts the turn, append a bounded `provider.switched` info activity to that provider turn so the timeline visibly records the source provider, target provider, and selected model.
- Provider resume cursors are optimistic hints, not user-visible failure points. If an upstream provider proves a persisted cursor is invalid for the current provider home/account, such as Codex app-server returning `no rollout found for thread id` or `failed to resolve rollout path ...: file does not exist` after a Codex home/account switch or missing rollout cleanup, Cafe must log the reconciliation, retry once with a fresh provider session, and durably replace or clear the stale cursor. Keep this detector scoped to a known persisted cursor and upstream rollout-resolution errors so unrelated provider failures remain fail-closed. Do not surface that recoverable stale-cursor condition as a blocking toast or chat failure.
- Duplicating a thread is a Cafe context fork, not a provider runtime fork. The duplicate may copy persisted messages, terminalized turn/checkpoint context, proposed plans, and historical non-callback work-log rows, but it must not copy provider sessions, provider resume cursors, active turn ids, pending approvals, or pending user-input callbacks. Any copied `running` or `pending` turn state must be terminalized as `interrupted` in the duplicate so the next user prompt starts a fresh provider session from copied context rather than steering or resuming the source provider process.
- The user-facing `Fork thread` action is a provider-native branch, distinct from the legacy Cafe-only duplicate event. It is available only for an idle Codex or Claude thread with durable provider context, keeps the exact same project/workspace/worktree, and leaves the source untouched. The authenticated transport must call `ProviderService.forkSession` before committing `thread.created` + `thread.forked` + a stopped `thread.session-set`; key the provider binding to the initiating command id so transport retries reuse one native branch and a competing request cannot claim or delete it. If the Cafe commit fails, discard only the native fork owned by that command and remove its dormant binding. Never silently fall back to copying visible Cafe messages when the native fork is unavailable, because that would claim provider context which the next turn cannot resume.
- Pending approvals and user-input callbacks are provider-runtime state. After restart or daemon handoff, stale callback IDs may be invalid; convert those failures into clear lifecycle events and user-visible recovery guidance.
- Reconciliation after restart must prefer durable provider/session state and command ledgers over UI assumptions. Never automatically resend a user prompt after a crash unless the design cryptographically or durably proves the provider never received it.
- WebSocket shell/detail subscriptions must be replayable from persisted orchestration-event cursors, not hot PubSub-only. A thread detail snapshot's `snapshotSequence` must be read in the same database transaction as the detail payload; never stamp stale detail rows with a newer cursor because the client will correctly skip events at or below that cursor.
- When durable provider runtime state says a session is `stopped`, that runtime record is authoritative over stale projection state. Clear any projected active turn, mark the abandoned projected turn `interrupted` rather than completed, preserve provider resume cursors, and let the next user send resume through a fresh provider process. This follows the Codex CLI/app-server ownership model: a stopped app-server process cannot still own a steerable turn.
- A stale `projection_turns.state = running` row is not sufficient proof that a provider turn is still steerable after restart, interrupt, or stop-all. If durable runtime state is stopped with no active provider turn, startup reconciliation must interrupt pre-stop running turns and close their streaming assistant rows; new user prompts must start/resume fresh provider state instead of being converted into steers to a dead app-server.
- Shutdown/finalizer code must persist `status = stopped` and `activeTurnId = null` before calling provider adapter stop/stopAll methods. If a malformed shutdown leaves `lastRuntimeEvent = provider.stopAll` behind with a stale `running` status, startup reconciliation must treat that marker as authoritative stopped runtime state and repair projections before the renderer can show a phantom active turn.

## Codex Integration

Cafe Code's Codex adapter uses `codex app-server`, which speaks JSON-RPC over stdio by default. Official docs describe the app-server protocol as JSON-RPC-like messages where requests have `id`, responses echo the `id`, and notifications omit `id`. The official app-server websocket listener is experimental/unsupported; Cafe should keep using stdio JSONL for local app-server control unless upstream changes that recommendation.

The generated `packages/effect-codex-app-server` protocol surface is currently aligned to the upstream Codex `rust-v0.150.0` release commit `3b3b4f8fb3f6403e72c2d0533ed0d2f309c59717`. This retains the 0.147-0.149 thread-section, blocking-user-input, queue/project, revert, async-delivery, duration, account-usage, strict auto-approval-review, education-plan, and multi-agent fields, and adds the 0.150 subagent completion/collaboration variants, terminal-input approvals, interrupt hooks, skill plugin ownership, MCP runtime status, and experimental realtime/MCP event-stream schemas. Regenerate from the exact stable release commit when a future target changes protocol types; never hand-edit generated schemas. Upstream spells the usage RPC as `account/usage/read` with optional `GetAccountTokenUsageParams`; Cafe's generator must preserve that RPC as `params object | undefined` even though ts-rs stores its object schema under `NullableGetAccountTokenUsageParams`.

Codex `rust-v0.150.0` TUI startup reconciliation in `codex-rs/tui/src/app/session_lifecycle.rs` treats a buffered active turn or `ThreadStatus::Active` as positive liveness evidence; a completed snapshot is terminal evidence. Cafe must preserve that ordering across its split backend/provider-daemon architecture. Process-local session absence is never equivalent to an upstream completed snapshot, and only `turn/completed`, an authoritative interrupted/failed provider event, or the explicitly guarded Cafe reconciliation paths may close a live turn.

The 2026-08-13 `0.146.0..0.147.0` TUI/app-server audit found no change to the normal steer routing contract: the TUI still tries `turn/steer` against its known active turn, retries once with the server-reported turn id on an expected-turn mismatch, starts a new turn only after app-server reports no active turn, and queues steers rejected by review/compact turns. Upstream's nonblocking interrupt change moves TUI dispatch off the terminal input loop; Cafe already dispatches Stop asynchronously and keeps app-server terminal state authoritative, so it does not require a lifecycle rewrite. Cafe's existing queue, stale-turn reconciliation, and provider-thread routing remain the correct shape. Cafe preserves valid `emittedAtMs` values as canonical provider-event time, dual-sends local runtime roots in the selected environment plus the legacy compatibility field, records `cacheWriteInputTokens` without counting it as generated output, preserves `spendControlReached` and individual spend-limit metadata without enforcing billing policy locally, and routes environment notifications by their native provider thread. Cafe intentionally leaves `experimentalRawEvents` disabled because per-response raw events are high-volume and non-replayed; paginated Codex history remains an upstream resume capability rather than a replacement for Cafe's durable thread database. Audio/realtime input is schema-compatible but is not advertised until Cafe has an explicit attachment/playback UX. Remote Code Mode hosting and standalone custom-provider web search remain provider-owned capabilities and are not advertised by Cafe until they have explicit authenticated product surfaces. The upstream remote-compaction-v2 implementation still builds the normal model-visible tool catalog in `compact_remote_v2_attempt.rs`, so the hosted image-tool reliability quarantine below remains necessary.

Codex forks use stable app-server `thread/fork` with `ephemeral: false`, the source native thread id, and the source cwd. The returned native thread id is the target's durable resume cursor; unsubscribe the newly loaded target from the source app-server process after creation so a later target-owned runtime can resume it without retaining two live threads. Compensation uses `thread/delete` only for an uncommitted fork whose command-id ownership still matches the dormant target binding. Do not emulate a fork with `thread/read`, copied Cafe messages, or a fresh `thread/start` because none of those preserve the provider's native conversation context.

The 2026-08-21 `0.147.0..0.149.0` TUI/app-server audit again found the normal steer algorithm unchanged: steer a known active turn, retry once with app-server's actual turn id after an expected-turn mismatch, start only when app-server reports no active turn, and keep rejected review/compact input in the local pending queue. The new provider-native `thread/queue/*` request family remains experimental and is not a replacement for Cafe's durable input queue. Cafe decodes stable `thread/queue/changed`, `thread/reverted`, `project/changed`, and `thread/project/updated` notifications but does not let those provider-private metadata stores mutate Cafe's separate orchestration database. `autoApprovalReview/strictReviewRequired` is a security-relevant, non-terminal TUI status: persist one bounded work-log warning while leaving the active turn and task running. An `agentMessage` with `delivery: "async"` remains a normal item lifecycle edge and must never be treated as turn completion; only `turn/completed` is terminal truth. Education plans `edu_plus` and `edu_pro` retain distinct provider labels. Re-audit these decisions before enabling the experimental app-server queue or mapping provider-native projects into Cafe projects.

The 2026-08-27 `0.149.1..0.150.0` TUI/app-server audit found the normal steer algorithm and stdio app-server recommendation unchanged. Multi-agent-v2 now emits explicit `subAgentActivity.kind = completed`; match the TUI by treating both `completed` and `interrupted` as terminal child-liveness evidence. The new `sendMessage`, `followupTask`, `interruptAgent`, and `listAgents` collaboration calls are analytics-only in the official TUI: do not create duplicate Cafe work-log rows because their user-visible lifecycle is authoritative through `subAgentActivity`. Collab-call status may be `interrupted`. Command approvals now distinguish `kind = command|writeStdin`; a stdin callback owns a distinct `approvalId`, which must be used for callback correlation instead of the parent command item id. Guardian `writeStdin` review actions contain literal stdin, cwd, process id, and approval id: never persist or log those raw fields, and retain only bounded presence/lifecycle metadata. Decode `interrupt` hook events and explicit skill `pluginId` ownership. The new `mcpServer/event/stream/notification` and `thread/realtime/item/*` notifications remain experimental and can contain provider/user content; route their native identities and redact diagnostics, but do not persist or advertise them until Cafe has an explicit authenticated UX and retention policy.

Codex `0.147.0` adds required `isBlocking` metadata to `item/tool/requestUserInput`. Match the TUI exactly for non-blocking questions: keep the first 60 seconds visually quiet, show a 60-second countdown after that grace period, and submit an empty answer map when the full 120 seconds expires. Any question navigation, option selection, or answer typing permanently snoozes automatic resolution for that request. The backend/provider runtime owns the actual deadline so an unmounted or stalled renderer cannot wedge app-server; the renderer owns only the countdown display and sends one idempotent snooze command. Older persisted/provider events default to blocking. Auto-resolution must emit the normal resolved event with explicit `autoResolved` metadata so projections clear the callback and explain the continuation in the work log.

Codex `0.146.0` command-execution items may include `pluginId` and `scriptPath`. Upstream documents these as trusted first-party plugin identity and a safe plugin-relative script path. Cafe surfaces that attribution in the bounded work log, but validates the path as relative and non-parent-traversing before displaying it; the provider event remains the canonical source and Cafe must never infer plugin trust from command text. The `ent26` plan uses upstream's `Enterprise` display name.

Codex MCP and dynamic-tool items carry their useful identity and input in `server`/`namespace`, `tool`, and `arguments`, rather than the generic lifecycle title. Cafe must include a bounded qualified tool name and redacted argument preview in work-log detail so these calls do not collapse to indistinguishable “MCP tool call” or “Tool call” rows. Common credential-bearing keys and token-shaped values must be redacted before the preview is persisted.

Codex `0.146.0` also adds `Thread.isPinned`, `ThreadListParams.isPinned`, and `ThreadMetadataUpdateParams.isPinned` to app-server's private thread store. Cafe decodes these fields for protocol compatibility but does not use them as sidebar ordering truth: Cafe's thread list is provider-agnostic and comes from its own durable projections, while a Cafe thread can switch provider instances or retain multiple provider-specific resume identities. A future Cafe pin feature must therefore persist a Cafe-owned pin field and may synchronize provider metadata only as a secondary best-effort mirror after a Codex session is materialized.

Preserve upstream Codex user-input routing as one transport command path with one recovery owner. `ProviderCommandReactor` owns the no-active-turn fallback and submits the same message through `turn/start` exactly once; the renderer's pending-steer state is observability only and must not independently resubmit when a terminal projection arrives. Renderer resubmission is limited to upstream-equivalent explicit rejection paths, such as non-steerable review/compact turns, and the documented interrupt flow after the provider has discarded pending input.

Cafe Code's Codex UX and lifecycle design should follow the Codex CLI/TUI command-line implementation, not Codex GUI behavior. The CLI is the primary upstream comparison point because it has the operational model Cafe Code needs: user input is accepted into local queues, live `turn/steer` is attempted only against a known active turn, stale active-turn state is reconciled automatically, non-steerable review/compact turns re-queue the user's input, and local app-server/session state is treated as disposable while durable Codex thread identity is preserved through upstream thread state.

- A stale `thread.turn-steer-requested` event can survive a restart or reconciliation boundary after the projected/provider active turn has already been cleared. This is a bounded repair for a proven local routing bug, not a general crash-resend policy; do not resend arbitrary prompts unless durable state proves Cafe, not the provider, stranded them.

Cafe tracks each accepted steer until the matching Codex `userMessage` `item/started` notification appears, emits `codex.turnSteer/noProviderItemYet` warnings after bounded delays, then emits `codex.turnSteer/processingStarted` with ACK-to-provider-item latency. - Claude Code stderr lines beginning with `[ede_diagnostic]` are internal execution summaries that can appear during healthy tool-use turns. Cafe must drop them before runtime warnings, work logs, toasts, and thread error surfaces instead of treating `stop_reason` values such as `tool_use` as user-visible failures.
- Claude built-in model metadata is data-driven from `apps/server/src/provider/Layers/ClaudeModelCatalog.json`. Add new first-party Claude model slugs, display names, model-specific option descriptors, context-window selectors, minimum Claude Code version gates, and provider-wide shared option descriptors there rather than hard-coding another model entry in `ClaudeProvider.ts`. Cafe strictly decodes the catalog schema, rejects duplicate option ids, clones shared controls into every built-in model, and also applies those shared controls to custom Claude slugs. Cafe hides entries whose `minimumClaudeCodeVersion` is newer than the installed CLI and shows an upgrade message for the newest hidden model. Keep `packages/contracts/src/model.ts` aliases in sync when upstream changes moving aliases such as `opus`, `sonnet`, or `fable`. A no-prompt Agent SDK 0.3.220 initialization against Claude Code 2.1.220 reports `default` and `opus[1m]` as `claude-opus-5[1m]`; Opus 5 supports only a 1M context, adaptive thinking, `low`/`medium`/`high`/`xhigh`/`max` effort, fast mode, and Auto permission mode, with `high` as Claude Code's default effort. Cafe gates `claude-opus-5` on Claude Code v2.1.219, maps `default`, `opus`, `opus5`, and bracketed Opus aliases to the canonical unbracketed slug, always resolves its API model id with `[1m]`, and exposes fast mode. Upstream 2.1.219 restricts fast mode to Opus 5 and Opus 4.8, so older Opus 4.7/4.6/4.5 entries must ignore stale persisted fast-mode selections. Cafe intentionally retains `claude-sonnet-5` as its new-thread provider default while matching Claude's moving `opus` alias, and keeps prior explicit model slugs available for existing threads. Fable 5 remains gated on v2.1.170 with 200k/1M choices and Sonnet 5 remains gated on v2.1.197; prompt-injected `ultrathink` stays separate from the SDK's concrete effort values.
- Claude provider launches must set an explicit `CLAUDE_CONFIG_DIR` for the effective Claude home while preserving a user-configured provider-instance `CLAUDE_CONFIG_DIR`. This keeps Cafe SDK sessions aligned with verified CLI launches such as `CLAUDE_CONFIG_DIR=/Users/me/.claude claude`. If Claude emits `api_retry`/result authentication failures with HTTP 401, treat the active SDK session as stale login material: record work-log diagnostics, suppress Claude Code's synthetic assistant error text, close the stale session, and let the next turn start a fresh Claude process with current credentials.

## Observability And Debugging

- Every provider lifecycle change must leave enough debug breadcrumbs to answer: what command was sent, when it was accepted, when the provider emitted the first runtime event, when the first token/content/tool event arrived, when it completed, and what process owned it.
- The debug endpoint should include provider daemon health, provider supervisor health, process diagnostics, RPC metrics, command ledger summaries, recent failures with stack traces where available, runtime event method counts, recent lifecycle warnings, stale active turns, provider home paths, and provider process ownership.
- Settings diagnostics may show lightweight runtime-layer process, daemon, supervisor, and orchestration counters without `--cafe-debug`, but those summaries must stay bounded and sanitized. Keep raw prompts, full model output, bearer tokens, auth files, environment dumps, and deep event replay behind explicit local debugging flows.
- Add new debug fields when fixing new failure classes. Do not rely on logs alone when a compact health/debug summary would make future diagnosis faster.
- Runtime event names should be specific enough to grep, such as `codex.turnStart/accepted`, `codex.turnStart/noRuntimeEventYet`, provider stream disconnect warnings, snapshot backfill markers, and post-completion late-event diagnostics.
- Prefer structured error diagnostics with cause chains and stack traces. If an exception crosses a daemon/RPC boundary, preserve its type, message, stack when safe, and structured context.
- For performance issues, instrument before guessing. Track send-to-ACK latency, ACK-to-runtime-start latency, runtime-start-to-first-token latency, tool-call duration, database wait/busy time, projection latency, WebSocket push latency, renderer receipt timing, store/reducer time, render commit time, and token-to-screen latency.
- Debug continuation heuristics must treat the latest provider turn terminal event as the authoritative completion boundary. Older checkpoint/diff summaries for the same turn are artifact metadata, not proof that later same-turn tools or assistant messages were post-completion corruption.

## Persistence And SQLite

- Keep provider command ledgers idempotent. Mutating provider daemon RPCs must carry command IDs when replay or retry is possible.
- Avoid long SQLite transactions around provider I/O, process startup, network calls, or stream consumption.
- Do not load entire chat histories or event stores on every token/tool call. Use bounded queries, projections, cursors, and summary snapshots.
- Usage statistics keep headline daily totals in `usage_stats_days` and output-token attribution in `usage_stats_token_breakdown_days`, keyed by local day, canonical provider driver, and effective model. Attribution must never persist or display `providerInstanceId` or another configured account identifier: multiple accounts using the same driver intentionally aggregate together. Resolve a missing model at most once per turn from the live session, update it on `model.rerouted`, and use the bounded `unknown` bucket when no trustworthy model is available; never add provider-session queries to the per-token hot path. Aggregate and attribution deltas must commit in one SQLite transaction. Migration 61 begins attribution prospectively because older aggregate rows cannot be backfilled truthfully. Hydrate lifetime provider/model totals once at service startup, serve them from memory through `usageStats.get`, and keep the model-cardinality payload out of the 10 Hz `subscribeUsageStats` stream. The Usage page may refresh that in-memory detail at a low cadence while mounted and must show pre-migration aggregate tokens as earlier unattributed usage rather than assigning them speculatively.
- The shared usage-cost presentation used by Settings and Task Atrium must identify every monetary estimate as USD while retaining the familiar dollar sign. Token totals keep their compact `K`/`M`/`B` summary and also show the exact comma-separated integer so small changes remain legible. Settings detail and graph data refresh every five seconds while the page exists; the Atrium's ambient usage read uses the same cadence only while visible, catches up immediately on visibility restore, and admits at most one request at a time. Only the fixed-cardinality aggregate processed/cached/uncached/output counters may use the reduced-motion-aware count-up hook; provider/model rows and chart data must remain static derivations of each atomic response rather than creating animation loops proportional to usage cardinality. Exact totals must wrap safely on narrow screens and must not replace compact notation.
- Keep provider daemon event journals bounded in SQLite as well as in memory. The persistent `provider_daemon_events` table is a restart/replay buffer for daemon/supervisor handoff, not an analytics warehouse; retaining unbounded provider events causes post-prompt latency and stale projection pressure that the Codex CLI does not have. Large inherited journals must be pruned by non-blocking journal maintenance after IPC/TCP readiness, because one-time migration deletes can exceed the desktop provider-daemon readiness timeout and leave bootstrap without a socket. Restart replay from a detached supervisor must be idempotent on provider runtime `eventId`, not local cursor, because supervisor cursors and daemon cursors are separate ownership domains.
- SQLite `database is locked` is a real lifecycle/performance signal. Add diagnostics for the writer, SQL operation, busy timeout, and affected command path instead of only increasing timeouts.
- Migrations must be deterministic, backward-safe where possible, and covered by tests. Reconciliation migrations should explain the exact stale state they repair.

## Performance Rules

- Cafe Code must be designed as a long-running provider stream processor, not a conventional short chat UI. Multi-hour and 16+ hour turns are expected. Small per-token costs compound into user-visible lag over those runs, so every token/event hot path must account for token-to-screen time, render-loop pressure, and accumulated projection cost.
- Provider token streaming must stay streaming. It is acceptable to coalesce tiny token deltas into small bounded projection chunks after the first visible bytes, but never batch tokens behind expensive projection work, full-history reads, synchronous filesystem scans, or renderer-only timers.
- Keep hot paths allocation-conscious and query-bounded. Any per-token or per-tool-call code should be reviewed as a performance-critical path.
- Provider event ingestion, projection, WebSocket fanout, renderer state updates, markdown rendering, scroll anchoring, and debug publication must stay independently bounded. Do not introduce work that scales with full chat history, full activity history, or total turn duration on each token/tool update.
- Do not perform broad process scans, recursive filesystem traversal, or source-control operations inside message send or provider event ingestion paths unless explicitly debounced and instrumented.
- Hidden checkpoint ref pruning can run after turn completion, so it must stay bounded: delete refs in batches with `git update-ref --stdin`, validate generated checkpoint ref names before stdin use, and log only counts plus small samples on prune failure. Projection-only placeholders such as `provider-diff:*` are not git refs; filter them before retention math and deletion so they cannot poison a whole prune batch or make Cafe retain/delete the wrong hidden checkpoint turns. Never spawn one git process per historical checkpoint ref or emit thousands of refs into runtime logs.
- Checkpoint capture only stages tracked content. It must first enumerate changed tracked paths and then update Cafe's temporary checkpoint index with path-limited `git add -u -- <changed-paths>` batches; do not use whole-worktree `git add -u -- .` in normal checkpoint capture, because large repositories can spend tens of seconds of CPU on every provider turn. Untracked-only repositories should produce an empty hidden checkpoint instead of a fatal checkpoint loop. Do not broaden checkpoint capture to `git add .`, because untracked files can include secrets or user scratch data.
- When comparing performance to Codex CLI or Claude CLI, identify the comparable phase first: process startup, session resume, prompt submission ACK, provider runtime start, model first token, tool execution, or UI projection.

## Frontend Lifecycle Rules

- The backend-authoritative `interfaceScalePercent` client setting is bounded to 80-130%, defaults to 100%, and is applied as the root HTML `font-size` percentage. This intentionally scales Cafe's rem-based typography, controls, icons, and spacing together while leaving browser zoom and stylesheet defaults intact; 100% must remove the inline override rather than pinning a redundant value. Keep the control in Settings -> Appearance, validate persisted values at the shared contract boundary, and verify compact title bars, fixed-format controls, composer typography/bounds, and overflow behavior at both bounds when changing shared layout. Desktop composer text and inline file/skill chips must remain rem-based so they scale with the rest of the interface. The composer may retain an absolute 16px text override only for coarse-pointer touch devices because iOS zooms focused editable text below that size; keep the editor's desktop min/max heights and padding rem-based.
- The renderer should display backend/provider truth and should not synthesize terminal, running, or active-turn state that can conflict with orchestration projections.
- Canonical `turn.plan.updated` is the provider-neutral lifecycle boundary for a runtime checklist. Provider adapters normalize their native plan/task updates into that event; the renderer consumes the projected current-turn checklist and must not add provider-specific parsing or presentation branches. While the turn is running and no approval, permission, elicitation, or user-input request is blocking the composer, render the latest nonempty checklist as a compact `Step X / Y` control above the composer. Resolve `X` as the first `inProgress` item, otherwise the first item not completed, otherwise the final item; derive the ring independently as `completed / total`. Remove the control when the turn becomes terminal or no nonempty current-turn checklist remains rather than preserving runtime task state as transcript or sidebar content.
- The composer task-progress control exposes every checklist description in original order inside one responsive, bounded-height scroll region; never truncate the checklist to a fixed row count, replace rows with an “and more” summary, or create nested/outer scrollbars around that region. Hover may preview it, but the trigger must be a native focusable button with keyboard focus plus click/tap open behavior, correct expanded/popup accessibility state, Escape/outside dismissal, and viewport-aware sizing for small screens. Mixed hover/press state is controlled deliberately: a click or keyboard press arriving after a hover/focus preview pins the popover open, and pointer leave must not close that press-pinned state. This intentionally fixes the installed Codex app's hover-only trigger, which ignores touch and is not normally keyboard-focusable. Runtime checklists must never open the right sidebar. Only authored proposed-plan documents retain the Plan side panel and its auto-open preference; changing that preference must not affect runtime checklist visibility or composer progress.
- The same Tasks popover shows every currently active Codex and Claude subagent across all turns above the checklist, not only children of the latest turn or only agents whose spawn row remains in the visible transcript window. Keep each shared roster row's deterministic local avatar, bounded description/objective or latest progress, explicit status, and live elapsed time visible without hover. The trigger may remain present for active subagents even when no checklist exists. Each roster row is a semantic button that closes the popover and opens that exact child's detail; ended children remain available from their durable transcript row/history surfaces even after they leave this active-only composer roster.
- Desktop navigation uses a fully off-canvas sidebar, not a permanent collapsed icon strip. While open, the standard Lucide panel-close trigger belongs beside the Cafe wordmark in the title/header band; after the sidebar slides completely left, the matching panel-open trigger appears in the active chat, settings, or empty-state content header. Mobile keeps the same control against its sheet state. Preserve the 200 ms width/position animation, keep the sidebar chrome mounted while it exits so the panel does not turn blank mid-slide, preserve the unread-completion dot and global persisted open state, and retain the content-header escape hatch; never place the only reopen control inside the hidden sidebar. On macOS Electron only, the collapsed content-header trigger must retain the same traffic-light-safe 90px start position as the open sidebar header; Windows, Linux, browser, and mobile layouts must not inherit that inset.
- Completed-turn unread state is derived from each thread's projected `completedAt` and the renderer's scoped `threadLastVisitedAtById` cursor. Persist and validate those cursors with the rest of durable UI state, restore them before sidebar status derivation on startup, and prune them against authoritative thread shells; a renderer reload must not make previously viewed completions unread again. Keep this preference client-local and bounded rather than adding read commands to provider or orchestration hot paths.
- Scroll-follow behavior should be tolerant of small gaps from the bottom and must not jump to the top when steer messages, late messages, or terminal markers arrive.
- Timeline scrolling has two explicit modes. While following the tail, live row measurements must keep the final working/message row pinned even when a bounded tool/work-log preview rotates or changes height; coalesce any post-layout correction to one animation frame. Upward wheel/touch/keyboard/scrollbar review intent must synchronously cancel pending tail corrections. While detached for review, disable tail following and enable both data-change and size-change visible-content anchoring so provider updates do not move the text being read. Data-change anchoring must remain disabled in follow mode because it can fight submit-time bottom pinning.
- Message timelines must handle late provider events after completion without duplicating terminal banners or losing streamed content.
- Per-thread detail subscriptions must apply snapshots and events monotonically by orchestration sequence. Events at or below the detail snapshot sequence are stale for that subscription and must not regress focused-thread session or turn state.
- The sidebar is a shell-summary surface and must not eagerly retain full thread-detail subscriptions for visible rows. On long-running databases, prewarming several histories at startup performs unnecessary bounded-history queries, snapshot serialization, and renderer hydration in parallel; it can exhaust the shared WebSocket bulk window and repeatedly interrupt the shell stream that makes the chat list available. The focused chat and explicit detail surfaces such as visible Task Atrium cards retain detail subscriptions on demand instead.
- Shell subscriptions intentionally omit the activity detail needed for subagent rows. Any renderer surface that shows activity for threads other than the focused chat must explicitly retain the shared detail subscription keyed by `(environmentId, threadId)`, hold it for the lifetime of every represented thread, and release it idempotently when that thread leaves the surface or the surface unmounts. Reuse the environment runtime's ref count, reconnect handling, monotonic snapshot/event buffering, warm idle cache, and bounded idle-only eviction; never create a component-private WebSocket, assume an offscreen card is hydrated, or subscribe only the currently visible slice of an uncapped list.
- Subagents are a dedicated roster, never ordinary entries inside the command/tool Work Log. Current and historical turn surfaces render the complete coalesced subagent roster separately from the paged/collapsed Work Log; the Work Log's presence, count, pagination, empty state, and “show more” controls must all use the same ordinary-work predicate and exclude structured subagent lifecycle rows. Preserve one scroll owner per bounded surface: the Work Log body may scroll when expanded, but no outer Work Log scrollbar may wrap it, and subagent cards/rows never receive per-row scrollbars. Full cards/rows remain aligned, shrink-safe, and responsive without page-level horizontal overflow.
- Subagent roster rows use the shared deterministic local avatar and keep bounded description/objective or latest progress, explicit status, and elapsed time visible without hover; terminal duration freezes at the recorded completion edge. Selecting either a live or ended row navigates within the chat column to a full-width provider-neutral detail surface with explicit back/Escape behavior, focus restoration, and the authenticated provider transcript when available. Keep the hidden timeline mounted and inert while detail is open so returning preserves its scroll position. The detail transcript has one scroll owner, initially follows the newest message, and remains pinned to the bottom only while the reader is attached; scrolling up must preserve the reader's position, surface a bounded new-update indicator, and allow one action to jump back to live output.
- Open subagent detail refreshes from canonical lifecycle revisions rather than a blind polling loop. Coalesce noisy progress invalidations behind a bounded minimum interval, refresh terminal transitions immediately, keep at most one provider-history read in flight with one trailing refresh, pause while the document is hidden, catch up when visibility returns, and offer an explicit retry after transient transport unavailability. A refresh must replace only the same exact child selection; changing child/turn/history identity clears the previous transcript so stale text can never appear under a different agent. Render typed per-message omissions and chronological gap markers inline, retaining the beginning and latest tail while the open view continues receiving new provider-backed content.
- Recoverable non-transport subscription failures must use capped exponential backoff instead of retrying a permanently invalid snapshot four times per second. Receiving an early snapshot chunk does not by itself prove recovery, because the same subscription may fail on a later chunk or event; reset the failure ramp only after a quiet failure window. Transport reconnect handling remains independent.
- Codex steer UI state should mirror upstream CLI semantics: a `turn/steer` ACK is not enough to clear a pending steer marker. Keep the renderer in a visible "steering" state until Codex emits the provider-side user-message/processing-start signal or the backend records a documented recovery/failure event. A terminal turn projection alone must neither clear nor replay the steer: app-server may report the old turn terminal while the backend is already falling through from `turn/steer` to `turn/start`, and renderer replay would duplicate the user's instruction.
- A WebSocket interruption while `orchestration.dispatchCommand` is awaiting its response is an indeterminate acknowledgement, not proof that the command failed. The server commits the orchestration event and durable command receipt atomically, so the renderer must retry the exact same command object and `commandId` after reconnect. Never generate a replacement id, remove the optimistic steering row, restore the composer, or invite a manual resend until a definitive rejection or the bounded reconnect window is exhausted; otherwise one lost ACK can submit the same Codex steer multiple times.
- Shell and per-thread detail WebSocket subscriptions are critical recovery streams. They must retry recoverable stream/protocol failures, force a fresh snapshot after reconnect, and never leave the renderer pinned to stale active-turn state while the backend projection/database has already advanced. Heartbeat timeouts should recycle the WebSocket session so subscriptions reattach instead of waiting on a half-dead socket.
- Recoverable provider, transport, and auto-retry diagnostics should not interrupt the user with toasts. Surface them in the work log, thread banners, connection diagnostics, or debug output unless immediate user action is required.
- UI disconnects, focus changes, reloads, or renderer stalls must be projection-catch-up events, never provider-session truth. The renderer should reconnect from a cursor or bounded snapshot, preserve queued follow-up/steer intent, and must not restart, interrupt, or orphan provider work merely because the local render loop lagged.
- Work-log rendering keeps the latest/current turn inline from the thread detail snapshot. Older turns render as collapsed inline `Work log` rows between that turn's user/assistant messages and hydrate their activity pages only after expansion through `orchestration.getThreadTurnActivityPage`; do not expand the thread detail snapshot activity cap to show historical logs. Before inserting unknown historical rows into the virtualized timeline, resolve their availability in bounded batches through `orchestration.getThreadTurnWorkLogPresence`. That RPC must use indexed turn-scoped `EXISTS` checks, return only opaque turn IDs, avoid activity payload/count reads, deduplicate turn IDs, and remain capped by the shared contract limit.
- Historical work-log presence/count/page queries must use the same displayability predicate. Exclude context-window bookkeeping, checkpoint-captured markers, every structured `task.started` / `task.progress` / `task.completed` row carrying `payload.subagent`, ordinary `tool.started`, retryable steer-delivery placeholders, and ExitPlanMode boundary tool rows from every DB-backed historical path. Snapshot-proven rows may render immediately; otherwise cache presence per focused thread, omit unresolved/empty rows from the virtualized data set, and remove a row if the expansion-time count proves it empty. A transient transport failure may preserve a discoverable fallback row, but it must not produce a toast or discard persisted activity.
- Retryable Codex `activeTurnNotSteerable` follow-ups for `review` or `compact` are automatic steer retries, not ordinary queued messages. The renderer should label them as waiting to steer, hide manual Send actions that could duplicate the user bubble, retry compact-blocked steers only after the active context compaction item completes, and retry review-blocked follow-ups only when the active turn is ready for the next message.
- Renderer session reducers must treat same-turn `running` snapshots after terminal `ready`/`error`/`interrupted` state as stale provider replay. Preserve the terminal latest turn, active-turn clearing, and newest lifecycle timestamp; otherwise debug/work-state can falsely report post-completion messages or a stale steerable active turn even though the backend projection is correct.
- Keep renderer token streaming on a tight hot path. Thread-detail stream events may be frame-batched before they enter Zustand, but sequence guards must still preserve monotonic projection order. Only append-like streaming deltas may be coalesced together; terminal assistant completion events must remain separate because non-streaming message events use authoritative replace/preserve semantics. Existing message deltas should update normalized message maps directly instead of materializing the full `Thread`, scanning the entire 2,000-message window, and rebuilding every slice per token.
- Desktop debug snapshots are diagnostic output, not provider or UI truth. When `--cafe-debug` is enabled, renderer debug publication must be throttled/heartbeat-driven so large debug JSON snapshots do not compete with token streaming, timeline rendering, or follow-up/steer dispatch.
- Assistant output may arrive as sparse or final large deltas even when the provider is healthy. The backend should keep streaming chunks small and bounded; the renderer may smooth display of an already-received large assistant append for readability, but it must not synthesize provider lifecycle state or hide backend/provider timing diagnostics.
- Live steer UI must distinguish queued follow-ups from accepted in-flight steers. Once Cafe dispatches a provider-supported steer into an active turn, show a non-cancelable steering state until provider output, terminal turn state, or an explicit steer failure/requeue proves the handoff is resolved; otherwise users cannot tell whether Codex/Claude received the follow-up or the renderer lost it.
- User-facing follow-up controls must not tell the user that a provider cannot steer, cannot accept input, or can only queue. Accept the user's intent, then route it through live steer, queued follow-up, interrupt-and-resume, app-server restart, or another documented recovery path automatically. Provider limitations, active-turn mismatch details, review/compact rejections, and retry metadata belong in debug/work-log diagnostics, not as blocking UI copy.
- Toasts should be reserved for action-required or non-recoverable conditions. Auto-retryable provider issues, delayed steers, queued follow-ups, compaction waits, and recoverable transport/provider races should update the work log, queue UI, or debug diagnostics instead of popping transient toasts.
